## What this is

Harbour is a fictional marketplace platform running on GCP, and it is **deliberately misconfigured**. Every problem in the register is one I put there on purpose, because the point is not the architecture — it is the reasoning about what is wrong with it, why it is wrong, and what order the fixes have to happen in. That last part is the reason for the phase rail: you can walk the whole platform through six remediation steps and watch the failures clear one at a time.

I built it as a learning lab while working through GCP networking end to end. The defects are the kind that appear in real projects: each one started as a reasonable short-term choice that nobody revisited. None of them is obvious from a diagram, which is the whole reason the diagram alone is not enough.

**What this is not:** a production template, a best-practice reference, or an audit of any real system. Names, addresses and identifiers are invented.

## Where I would push back on the textbook answer

<Lede>
  Not every “correct” answer is the right one for a given system. These are the
  places in Harbour where the standard advice deserves an argument.
</Lede>

| The situation                              | The tension                                                                                                                                                                                                                                                                                             |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Session affinity on the legacy backend** | Affinity works against even balancing and breaks when the sticky backend goes away. The clean fix is stateless backends with shared session state — but that is an application change, not a network one. Naming which layer a fix belongs to matters more than naming the fix.                         |
| **PSA rather than PSC for the database**   | PSC would have been the better original choice, because it sidesteps the non-transitivity that causes D11. But the PSA peering already exists, so PSA is the shorter path to a private database. Taking the shorter path knowingly is a different thing from not knowing.                               |
| **Network tags for firewall targeting**    | Anyone who can edit a VM can add a tag and pull in every rule that targets it. Service accounts are a real identity and much harder to attach casually. Harbour uses tags everywhere, like most projects — that is convenience over strength, and worth stating as a choice rather than leaving unsaid. |
| **Two CDNs in the path**                   | Cloudflare and Cloud CDN can both cache. Running both without deciding which one actually does is the common mistake, and it makes cache invalidation ambiguous. The decision matters more than either answer.                                                                                          |
| **DNSSEC**                                 | Supported, free, and still skipped by most domains. Whether it is worth enabling depends on the threat model, not on whether it is available. Not every available hardening step earns its place.                                                                                                       |
| **Global load balancing by default**       | Global is the GCP instinct and the geographic routing is free. Regional is right when data residency or cost dominate — and choosing it deliberately is a better signal than reaching for global because it is the default.                                                                             |
