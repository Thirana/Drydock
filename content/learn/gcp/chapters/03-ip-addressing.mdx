## The external IP is not on the VM

<Recalls><Recall n="10">NAT, and 1:1 NAT</Recall></Recalls>

The internal IP is real in every sense: it is on the network card, it shows in `ip addr`, and the app can bind to it. The external IP is only a **mapping** kept by the data plane on the VM's host (<Ch n="1">chapter 1</Ch>). It is the 1:1 NAT from the fundamentals course, done beside every VM instead of in a box at the edge.

<Figure wide hues={["plum", "teal", "green"]} drawing={<FigExternal />}>

The external IP is attached as an "access config" of type ONE\_TO\_ONE\_NAT on the VM's network card. The name says exactly what it is.

</Figure>

Four things follow from this, and each one causes real bugs:

<Table>
  <thead>
    <tr><th>#</th><th>Consequence</th><th>What goes wrong</th><th>Do this instead</th></tr>
  </thead>
  <tbody>
    <tr><td>1</td><td>The VM does not know its external IP</td><td>An app that reads its own address to build URLs or callbacks gets `10.10.1.10`</td><td>Ask the metadata server (gcloud check below), or use a DNS name</td></tr>
    <tr><td>2</td><td>The app cannot bind to the external IP</td><td>`listen 34.87.120.15:8080` fails: that address is not on any interface (<Ch course="fundamentals" n="31">Fundamentals ch 31</Ch>)</td><td>Bind to `0.0.0.0` or the internal IP</td></tr>
    <tr><td>3</td><td>Outside services see the external IP</td><td>An allow-list (PayGate, a partner, Cloud SQL authorized networks) must hold the external IP, not the internal one. The VM never sees that address, so it is easy to get wrong</td><td>Use a static IP for anything an allow-list depends on (section 03)</td></tr>
    <tr><td>4</td><td>Firewall rules on the receiving side see the sender's external IP</td><td>If one of your own VMs calls another through an external IP, the internal allow rule does not match (section 06)</td><td>Use internal IPs between your own VMs</td></tr>
  </tbody>
</Table>

<Box kind="check" title="gcloud check">

See the mapping from outside, and ask for the external IP from inside the VM:

## Ephemeral and static

Every internal and external address is either **ephemeral** (it belongs to the VM for a while) or **static** (a named address resource you own until you release it). The two kinds behave very differently for internal and external addresses:

<Table>
  <thead>
    <tr><th>#</th><th></th><th>Ephemeral internal</th><th>Static internal</th><th>Ephemeral external</th><th>Static external</th></tr>
  </thead>
  <tbody>
    <tr><td>1</td><td>Comes from</td><td>Next free address in the subnet</td><td>An address you reserve in a subnet</td><td>Google's pool, when the VM starts</td><td>An address you reserve</td></tr>
    <tr><td>2</td><td>VM stopped and started</td><td><St k="ok">same address</St></td><td><St k="ok">same address</St></td><td><St k="bad">new address</St></td><td><St k="ok">same address</St></td></tr>
    <tr><td>3</td><td>VM deleted</td><td>Released</td><td>Kept, ready to reuse</td><td>Released</td><td>Kept, ready to reuse</td></tr>
    <tr><td>4</td><td>Listed by `addresses list`</td><td>No</td><td>Yes</td><td>No</td><td>Yes</td></tr>
    <tr><td>5</td><td>Cost</td><td>Free</td><td>Free</td><td>Charged while the VM runs</td><td>Charged while in use; charged more while idle</td></tr>
  </tbody>
</Table>

Row 2 is Kadé's outage: an ephemeral **external** address does not survive a stop. Ephemeral **internal** addresses do, which is why kade-db has kept `10.10.2.5` so far. It would lose it only if the VM were deleted and recreated.

<Key title="Promote instead of replace">

An ephemeral address already in use can be turned into a static one without changing it. You "reserve" the exact address the VM already has, and GCP converts it in place. No downtime, no new address, nothing to update in DNS or allow-lists.

</Key>

<Box kind="cost" title="Cost and limits (checked September 2026)">

Internal addresses are free. An external IPv4 address on a running standard VM costs about US$0.005 per hour, the same for ephemeral and static. A static external address that is reserved but not in use costs more, about US$0.01 per hour, because Google wants unused IPv4 addresses given back. A static address attached to a stopped VM still counts as in use. Check the VPC pricing page for your region before relying on these numbers.

</Box>

So the rule is simple: **if anything depends on an address, make it static.** A DNS record, an allow-list, a partner's config, or an app setting all count.

## Network tiers: Premium and Standard

<Recalls><Recall n="12">How routing works across the internet</Recall></Recalls>

Every external address has a <Term>network tier</Term>. The tier decides where traffic joins or leaves Google's network, and so how much of the trip happens on the public internet.

<Figure wide hues={["plum", "teal"]} drawing={<FigTiers />}>

The difference is who carries the packet. Premium: Google, from near the user. Standard: the public internet, until close to your region.

</Figure>

  <tbody>

The tier is set per address or resource, and a project has a default tier (Premium unless changed). A resource and its address must use the same tier, which is why a global load balancer can only ever have a Premium address. Everything shopper-facing at Kadé is Premium.

## Between your own VMs, always use internal addresses

A common mistake is one VM calling another (or itself) through an external IP, often because the external address was copied into a config file. It works, which is why it goes unnoticed. But the packet goes out through 1:1 NAT and comes back in as if it came from the internet:

<Table>
  <thead>
    <tr><th>#</th><th></th><th>kade-api-1 → `10.10.2.5:5432`</th><th>kade-api-1 → kade-db's external IP (if it had one)</th></tr>
  </thead>
  <tbody>
    <tr><td>1</td><td>Source kade-db sees</td><td>`10.10.1.10`</td><td>kade-api-1's external IP, or the NAT IP</td></tr>
    <tr><td>2</td><td>Firewall rule needed on kade-db</td><td>An internal rule for `10.10.0.0/16`</td><td>A rule that allows an external address, and so is open wider than it should be</td></tr>
    <tr><td>3</td><td>Cost</td><td>Internal traffic pricing</td><td>Counted as traffic leaving the zone, even inside one zone</td></tr>
    <tr><td>4</td><td>Needs</td><td>Nothing extra</td><td>Both VMs to have external IPs, or NAT</td></tr>
  </tbody>
</Table>

The same applies to a VM calling **its own** external IP, which usually means a setting that should say `localhost` or an internal name. The fix is always the same: internal IPs or internal DNS names (<Ch n="8">chapter 8</Ch>) between your own machines.

## Alias IPs in practice

<Ch n="2">Chapter 2</Ch> introduced alias IP ranges. Adding one, or moving it from one VM to another, is a change to the VM's network card through GCP, not inside the OS:

<Table>
  <thead>
    <tr><th>#</th><th>Step</th><th>Command (short form)</th></tr>
  </thead>
  <tbody>
    <tr><td>1</td><td>Give kade-api-1 the extra address `10.10.1.100`</td><td>`network-interfaces update kade-api-1 --aliases="10.10.1.100/32"`</td></tr>
    <tr><td>2</td><td>Take it away from kade-api-1</td><td>`network-interfaces update kade-api-1 --aliases=""`</td></tr>
    <tr><td>3</td><td>Give it to kade-api-2</td><td>`network-interfaces update kade-api-2 --aliases="10.10.1.100/32"`</td></tr>
  </tbody>
</Table>

<Caption>An address can only be on one network card at a time, so a move is always "remove, then add". The full commands are at the end of the chapter.</Caption>

On Google's standard images, the guest agent adds the alias to the OS's local routing table, so the VM accepts traffic for it without any manual setup. This remove-then-add move is the GCP way to do what gratuitous ARP did on a real LAN (<Ch n="1">chapter 1</Ch> section 10). For automatic failover, an internal load balancer with health checks is still the better tool (<Ch n="11">chapter 11</Ch>).

## IP forwarding and the anti-spoofing check

By default, the data plane checks every packet a VM sends and receives:

- A VM may only **send** packets whose source is one of its own addresses.
- A VM may only **receive** packets whose destination is one of its own addresses.

Anything else is dropped on the host. This is what stops one VM from pretending to be another. The `canIpForward` setting (`--can-ip-forward` when creating a VM) turns the check off, so the VM can pass traffic on for other machines. Only something built to forward traffic needs it: a router VM, a VPN appliance, or a self-built NAT VM.

<Table>
  <thead>
    <tr><th>#</th><th>Question</th><th>Answer</th></tr>
  </thead>
  <tbody>
    <tr><td>1</td><td>Does Kadé need it?</td><td>No. Cloud NAT and Cloud VPN are managed services, so Kadé never runs its own forwarding VM</td></tr>
    <tr><td>2</td><td>Why check for it?</td><td>A VM with forwarding on can relay traffic it should not. Security benchmarks (CIS 4.6) flag it</td></tr>
    <tr><td>3</td><td>Can it be changed later?</td><td>It used to be creation-only. Today you can change it by exporting the VM's config, editing `canIpForward`, and applying it with `update-from-file`, which restarts the VM</td></tr>
  </tbody>
</Table>
