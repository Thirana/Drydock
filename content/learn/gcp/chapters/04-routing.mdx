## One route table for the whole VPC

<Recalls><Recall n="5">The default gateway</Recall><Recall n="12">Routing tables and longest prefix match</Recall></Recalls>

A route is a destination range plus a **next hop**: "packets for this range go there". That part is the same as the fundamentals course. What is different is where the table lives and how you limit it:

<Label>Output</Label>

NAME                            NETWORK   DEST_RANGE    NEXT_HOP                  PRIORITY
default-route-3b1c8e0f5a2d4e61  kade-vpc  0.0.0.0/0     default-internet-gateway  1000
default-route-7f2e9d1c4b6a8e03  kade-vpc  10.10.1.0/24  kade-vpc                  0

<Label>What it tells you</Label>

- Two **subnet routes**, one per subnet. Their next hop is the network itself: "deliver inside the VPC". This is why kade-api reaches kade-db with no setup.
- One **default route**, `0.0.0.0/0` to `default-internet-gateway`, priority 1000. This is the only path to the internet.
- All three were created by GCP, which is why they have generated names. Kadé has no custom routes.

</Box>

So why can't kade-api reach PayGate (finding 5) if there is a default route? Because a route is only half of the answer. The default internet gateway only accepts traffic from a VM with an external IP, or traffic handled by Cloud NAT. kade-api has neither. The route exists; nothing can use it yet. <Ch n="7">Chapter 7</Ch> fixes that.

### Static routes (custom routes you create)

You give a destination, a next hop, a priority, and optionally tags. The next hop can be:

### Dynamic routes

Learned over BGP by a Cloud Router, not typed in. On a VPN or Interconnect, the Cloud Router tells the other side about Kadé's ranges and installs the ranges the other side advertises. When a tunnel goes down, its routes are removed automatically. The VPC's **dynamic routing mode** (regional or global, <Ch n="2">chapter 2</Ch> section 01) decides whether those routes apply in one region or all of them. This is <Ch n="15">chapter 15</Ch>'s topic; Kadé's Cloud Router in <Ch n="7">chapter 7</Ch> exists only to run Cloud NAT and learns nothing.

### Policy-based routes

A newer, more specialised type. A policy-based route can match on **source** range, destination range and protocol (not port), and its next hop must be an internal passthrough Network Load Balancer, usually a group of firewall appliances. It is checked **before** subnet routes, so it is the one tool that can send even VM-to-VM traffic through an appliance. Kadé does not need it.

### Special routing paths (hidden)

Some traffic uses paths that are not in your route table at all. You cannot see, delete or override them; only firewall rules can block them.

## How GCP picks a route

When a packet leaves a VM, GCP gathers every route that applies to that VM and contains the destination, then removes candidates step by step until one is left. The full list in Google's docs has twelve steps, many about peering and Network Connectivity Center. For a single VPC it comes down to this:

<Table>
  <thead>
    <tr><th>#</th><th>Step</th><th>What happens</th></tr>
  </thead>
  <tbody>
    <tr><td>1</td><td>Special paths</td><td>If the destination is one of the hidden paths in section 03, use it. Done</td></tr>
    <tr><td>2</td><td>Policy-based routes</td><td>If one matches (by priority only), use it. Done</td></tr>
    <tr><td>3</td><td>**Subnet routes**</td><td>If the destination is inside any subnet range, use the subnet route. Done. **Nothing can beat a subnet route**</td></tr>
    <tr><td>4</td><td>Applicable routes</td><td>Keep static and dynamic routes that contain the destination and apply to this VM (no tags, or a tag the VM has)</td></tr>
    <tr><td>5</td><td>**Longest prefix**</td><td>Keep only the most specific destination. Priority is not looked at yet</td></tr>
    <tr><td>6</td><td>Usable next hops</td><td>Drop routes whose next hop VM is stopped or deleted, or whose tunnel is down</td></tr>
    <tr><td>7</td><td>**Lowest priority number**</td><td>Keep only routes with the lowest number (0 to 65535, like firewall rules)</td></tr>
    <tr><td>8</td><td>Next hop preference</td><td>Instance and Classic VPN next hops beat dynamic routes, which beat an internal load balancer next hop, which beats the internet gateway</td></tr>
    <tr><td>9</td><td>Send</td><td>One route left: send. Several left: share traffic between them (ECMP). None left: drop, with an ICMP "network unreachable"</td></tr>
  </tbody>
</Table>

<Key title="Three rules that cause most surprises">

- **Specificity before priority.** A `/24` with priority 1000 beats a `/0` with priority 0. Priority only breaks ties between routes with the same destination.
- **Subnet routes cannot be beaten.** GCP refuses to create a static route that equals or fits inside a subnet range. To send VM-to-VM traffic through an appliance, you need a policy-based route or separate VPCs.
- **A dead next hop disappears, but only among equals.** If a route's next hop VM is stopped or its tunnel is down, the route is ignored at step 6. Traffic moves to another route with **exactly the same destination** if one exists. If the dead route was the only most-specific one, the packet is dropped: GCP never falls back to a less specific route (Example E).

</Key>

## Tag-scoped routes: patterns

With one table per VPC, tags are the only way to make a route apply to some VMs and not others. A route with tags applies only to VMs that have at least one of them; a route with no tags applies to every VM. Tags decide **which routes are candidates** for a VM. The winner is still picked by the steps in section 04.

<Box kind="console" title="Scenario A · Send some VMs through a proxy">

```text
Goal: kade-worker's internet traffic goes through kade-proxy; everyone else goes direct.

Route 1:  0.0.0.0/0 → default-internet-gateway   prio 1000   no tags (all VMs)
Route 2:  0.0.0.0/0 → instance kade-proxy        prio 900    tags: [via-proxy]

kade-worker (via-proxy):  both apply, both /0 → 900 beats 1000 → kade-proxy
kade-api-1 (no such tag): route 2 does not apply → route 1 → direct
```

kade-proxy needs IP forwarding on (<Ch n="3">chapter 3</Ch>) and its own way out: an external IP or Cloud NAT.

</Box>

<Box kind="console" title="Scenario B · Private VMs with no internet at all">

```text
Goal: kade-db can never reach the internet; other VMs can.

Delete the untagged default route, then:
Route 1:  0.0.0.0/0 → default-internet-gateway   prio 1000   tags: [internet]

kade-api-1, kade-worker tagged "internet" → internet as before
kade-db, no tag → no route to 0.0.0.0/0 → packet dropped (network unreachable)
```

The inverse is easier to get right than adding a "blackhole" route for the private VMs: no route means no path. Two warnings. Every VM that needs the internet must get the tag, and Cloud NAT only works for VMs that can see a default route to the internet gateway (section 08). An egress firewall rule (<Ch n="5">chapter 5</Ch>) is often the simpler tool for the same goal.

</Box>

<Box kind="console" title={"Scenario C · Why \"route to a blackhole VM\" leaks"}>

```text
Route 1:  0.0.0.0/0 → default-internet-gateway   prio 1000   no tags
Route 2:  0.0.0.0/0 → instance blackhole-vm      prio 900    tags: [no-egress]

Normal day:  kade-db (no-egress) → route 2 → packets sink at blackhole-vm
blackhole-vm stopped for patching:
             route 2 ignored (step 6) → route 1 → kade-db reaches the internet
```

Both routes have the same destination (`0.0.0.0/0`), so a dead next hop does not drop the traffic: its route is removed and the other one takes over (Example C in section 05 is the same mechanism). Anything that must fail closed should not depend on a VM being up. Use Scenario B or a firewall rule.

</Box>

<Box kind="console" title="Scenario D · Only some destinations through the appliance">

```text
Goal: only kade-worker's calls to PayGate go through kade-inspect.

Route 1:  0.0.0.0/0     → default-internet-gateway   prio 1000   no tags
Route 2:  192.0.2.0/24  → instance kade-inspect      prio 1000   tags: [inspected]

kade-worker (inspected):
  to 192.0.2.10 → route 2 (the /24 is more specific; priority not needed)
  to anything else on the internet → route 1
kade-api-1 (no tag): everything → route 1
```

Here specificity does the work, not priority. The tag only limits who sees the specific route.

</Box>

<Box kind="console" title="Scenario E · A tagged pair of VPN tunnels">

```text
Goal: only VMs tagged "via-office" send all traffic to the office, shared across two tunnels.

Route 2:  0.0.0.0/0 → vpn tunnel-a   prio 900   tags: [via-office]
Route 3:  0.0.0.0/0 → vpn tunnel-b   prio 900   tags: [via-office]

VM tagged via-office → routes 2 and 3 tie → ECMP across both tunnels
Untagged VM          → default route
```

Tagged static routes to Classic VPN tunnels work this way. HA VPN uses dynamic routes from BGP, which cannot carry tags; <Ch n="15">chapter 15</Ch> covers how that changes the design.

</Box>

<Box kind="console" title="Scenario F · A VM with two tags">

```text
kade-worker tags: [via-proxy, inspected]

Candidates for 192.0.2.10:
  0.0.0.0/0     → default gateway   prio 1000   applies (no tags)
  0.0.0.0/0     → kade-proxy        prio 900    applies (via-proxy)
  192.0.2.0/24  → kade-inspect      prio 1000   applies (inspected)
Longest prefix: 192.0.2.0/24 → kade-inspect WINS

Candidates for 8.8.8.8: only the two /0 routes → prio 900 → kade-proxy WINS
```

Tags decide candidacy, not the winner. With several tags, all their routes compete under the normal rules.

</Box>

<Box kind="exam" title="Exam angle">

"Only VMs X must send internet traffic through a NAT or proxy VM" is answered with a static route to `0.0.0.0/0`, next hop that VM, a lower priority number than the default route, and a network tag that only X carries. Watch for answers that say "attach a route table to the subnet": that is AWS, not GCP.

</Box>

## Deleting the default route

The default route is only a static route, so it can be deleted. People do this to "make sure nothing can reach the internet". Before doing it, know what depends on it:

<Table>
  <thead>
    <tr><th>#</th><th>Feature</th><th>Without a route to `default-internet-gateway`</th><th>Chapter</th></tr>
  </thead>
  <tbody>
    <tr><td>1</td><td>VMs with external IPs</td><td><St k="bad">breaks</St> no outgoing path to the internet</td><td className="whitespace-nowrap">3</td></tr>
    <tr><td>2</td><td>Cloud NAT</td><td><St k="bad">breaks</St> public Cloud NAT always needs a route to the internet gateway</td><td className="whitespace-nowrap">7</td></tr>
    <tr><td>3</td><td>Private Google Access with the normal API addresses</td><td><St k="bad">breaks</St> unless you add routes for the Google API ranges</td><td className="whitespace-nowrap">9</td></tr>
    <tr><td>4</td><td>Traffic inside the VPC</td><td><St k="ok">works</St> subnet routes are separate</td><td className="whitespace-nowrap">4</td></tr>
    <tr><td>5</td><td>Load balancer and health checks, IAP, Cloud DNS forwarding</td><td><St k="ok">works</St> special paths do not use the route table</td><td className="whitespace-nowrap">6, 8, 11</td></tr>
    <tr><td>6</td><td>External passthrough Network Load Balancer backends</td><td><St k="ok">works</St> they have their own special path</td><td className="whitespace-nowrap">11</td></tr>
  </tbody>
</Table>

<Caption>"No default route" does not mean "no internet exposure": load balancer traffic still reaches backends. Firewall rules are what actually control exposure.</Caption>

<Key title="Decision for Kadé: keep it">

Kadé depends on Cloud NAT (<Ch n="7">chapter 7</Ch>), so the default route stays. The goal behind deleting it, "only approved traffic leaves", is handled by removing external IPs, by Cloud NAT, and by egress firewall rules (<Ch n="5">chapter 5</Ch>).

</Key>

## Things to know before changing routes

<Table>
  <thead>
    <tr><th>#</th><th>Fact</th><th>What it means in practice</th></tr>
  </thead>
  <tbody>
    <tr><td>1</td><td>Static routes cannot be edited</td><td>To change one, create the new route first, check it, then delete the old one</td></tr>
    <tr><td>2</td><td>Changes spread out over a few seconds</td><td>Route changes reach every data plane "eventually". Several changes sent together may apply in any order</td></tr>
    <tr><td>3</td><td>An instance next hop needs IP forwarding</td><td>Without `canIpForward` the VM drops forwarded packets (<Ch n="3">chapter 3</Ch>)</td></tr>
    <tr><td>4</td><td>GCP does not check the appliance</td><td>It only checks the next hop VM is running, not that its software works. Use an internal load balancer next hop with health checks for anything important</td></tr>
    <tr><td>5</td><td>A route is not permission</td><td>The firewall still decides whether the packet is allowed (<Ch n="5">chapter 5</Ch>)</td></tr>

  </tbody>
