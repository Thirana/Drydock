## One route table for the whole VPC

<Recalls><Recall n="5">The default gateway</Recall><Recall n="12">Routing tables and longest prefix match</Recall></Recalls>

A route is a destination range plus a **next hop**: "packets for this range go there". That part is the same as the fundamentals course. What is different is where the table lives and how you limit it:

<Table>
  <thead>
    <tr><th>#</th><th></th><th>Home router (fundamentals course)</th><th>AWS VPC</th><th>GCP VPC</th></tr>
  </thead>
  <tbody>
    <tr><td>1</td><td>Where the table lives</td><td>In the router box</td><td>Several route tables, each attached to subnets</td><td>**One table for the whole VPC**, copied to every host's data plane</td></tr>
    <tr><td>2</td><td>How to make a route apply to only some machines</td><td>Separate router or VLAN</td><td>Attach a different table to their subnet</td><td>**Network tags** on the route and on the VMs</td></tr>
    <tr><td>3</td><td>"Public" vs "private" subnets</td><td>-</td><td>Which table the subnet uses</td><td>Not a subnet idea at all: done with tags, external IPs and Cloud NAT</td></tr>
    <tr><td>4</td><td>Who creates most routes</td><td>You, or DHCP</td><td>You</td><td>GCP, automatically</td></tr>
  </tbody>
</Table>

<Figure wide hues={["teal", "green", "amber"]} drawing={<FigOneTable />}>

There is only one table. A tag on a route does not create a second table; it only decides which VMs the route is a candidate for.

</Figure>

That one table lives in the control plane (<Ch n="1.2">chapter 1.2</Ch>). When you add a route, the control plane records it and pushes it to the data plane on every host that runs a kade-vpc VM, in every region. No VM asks a router where to send a packet: its host already holds the whole table. That is also why a change takes a few seconds to reach every host (section 09).

<Label>What it tells you</Label>

</Box>

So why can't kade-api reach PayGate (finding 5) if there is a default route? Because a route is only half of the answer. The default internet gateway only accepts traffic from a VM with an external IP, or traffic handled by Cloud NAT. kade-api has neither. The route exists; nothing can use it yet. <Ch n="7">Chapter 7</Ch> fixes that.

### Dynamic routes

Learned over BGP by a Cloud Router, not typed in. On a VPN or Interconnect, the Cloud Router tells the other side about Kadé's ranges and installs the ranges the other side advertises. When a tunnel goes down, its routes are removed automatically. The VPC's **dynamic routing mode** (regional or global, <Ch n="2">chapter 2</Ch> section 01) decides whether those routes apply in one region or all of them. This is <Ch n="15">chapter 15</Ch>'s topic; Kadé's Cloud Router in <Ch n="7">chapter 7</Ch> exists only to run Cloud NAT and learns nothing.

### Policy-based routes

A newer, more specialised type. A policy-based route can match on **source** range, destination range and protocol (not port), and its next hop must be an internal passthrough Network Load Balancer, usually a group of firewall appliances. It is checked **before** subnet routes, so it is the one tool that can send even VM-to-VM traffic through an appliance. Kadé does not need it.

### Special routing paths (hidden)

Some traffic uses paths that are not in your route table at all. You cannot see, delete or override them; only firewall rules can block them.

## How GCP picks a route

When a packet leaves a VM, GCP gathers every route that applies to that VM and contains the destination, then removes candidates step by step until one is left. The full list in Google's docs has twelve steps, many about peering and Network Connectivity Center. For a single VPC it comes down to this:

<Table>
  <thead>
    <tr><th>#</th><th>Step</th><th>What happens</th></tr>
  </thead>
  <tbody>
    <tr><td>1</td><td>Special paths</td><td>If the destination is one of the hidden paths in section 03, use it. Done</td></tr>
    <tr><td>2</td><td>Policy-based routes</td><td>If one matches (by priority only), use it. Done</td></tr>
    <tr><td>3</td><td>**Subnet routes**</td><td>If the destination is inside any subnet range, use the subnet route. Done. **Nothing can beat a subnet route**</td></tr>
    <tr><td>4</td><td>Applicable routes</td><td>Keep static and dynamic routes that contain the destination and apply to this VM (no tags, or a tag the VM has)</td></tr>
    <tr><td>5</td><td>**Longest prefix**</td><td>Keep only the most specific destination. Priority is not looked at yet</td></tr>
    <tr><td>6</td><td>Usable next hops</td><td>Drop routes whose next hop VM is stopped or deleted, or whose tunnel is down</td></tr>
    <tr><td>7</td><td>**Lowest priority number**</td><td>Keep only routes with the lowest number (0 to 65535, like firewall rules)</td></tr>
    <tr><td>8</td><td>Next hop preference</td><td>Instance and Classic VPN next hops beat dynamic routes, which beat an internal load balancer next hop, which beats the internet gateway</td></tr>
    <tr><td>9</td><td>Send</td><td>One route left: send. Several left: share traffic between them (ECMP). None left: drop, with an ICMP "network unreachable"</td></tr>
  </tbody>
</Table>

<Key title="Three rules that cause most surprises">

- **Specificity before priority.** A `/24` with priority 1000 beats a `/0` with priority 0. Priority only breaks ties between routes with the same destination.
- **Subnet routes cannot be beaten.** GCP refuses to create a static route that equals or fits inside a subnet range. To send VM-to-VM traffic through an appliance, you need a policy-based route or separate VPCs.
- **A dead next hop disappears, but only among equals.** If a route's next hop VM is stopped or its tunnel is down, the route is ignored at step 6. Traffic moves to another route with **exactly the same destination** if one exists. If the dead route was the only most-specific one, the packet is dropped: GCP never falls back to a less specific route (Example E).

</Key>

## Tag-scoped routes: patterns

With one table per VPC, tags are the only way to make a route apply to some VMs and not others. A route with tags applies only to VMs that have at least one of them; a route with no tags applies to every VM. Tags decide **which routes are candidates** for a VM. The winner is still picked by the steps in section 04.

Six common patterns follow. Pick a scenario, then a VM, and watch which route its packet gets. The "what if" buttons stop a next hop or remove a tag; that is where most of these patterns surprise people.

Three things the widget does not show. kade-proxy, kade-inspect and blackhole-vm need IP forwarding on (<Ch n="3">chapter 3</Ch>), and the first two need their own way out: an external IP or Cloud NAT. Cloud NAT only works for VMs that can see a default route to the internet gateway (section 08), which matters in Scenario B. And HA VPN uses dynamic routes from BGP, which cannot carry tags, so Scenario E works only with Classic VPN (<Ch n="15">chapter 15</Ch>).

## Routes and geography

A route belongs to kade-vpc, so it is **global**: one route applies to matching VMs in every region. What it points at is not always global. The next hop has a scope of its own (<Ch n="1.1" section="Three scopes: global, regional, zonal">chapter 1.1</Ch>), and that decides what a zone failure does to the route.

<Figure wide hues={["plum", "amber"]} labels={{ plum: "Google's: the control plane, regions, zones and data planes", amber: "The proxy route and the VMs it applies to" }} drawing={<FigRouteGeo />}>

Every host holds the route, but the route leads to one VM in one zone. A tagged VM in another region crosses regions to reach it.

</Figure>

<Table>
  <thead>
    <tr><th>#</th><th>Piece</th><th>Scope</th><th>If a zone fails</th></tr>
  </thead>
  <tbody>
    <tr><td>1</td><td>A route, of any type</td><td>Global</td><td>Nothing happens to it. It lives in the control plane and on every host, not in one zone</td></tr>
    <tr><td>2</td><td>Next hop: the default internet gateway</td><td>Global</td><td>Nothing to fail on Kadé's side</td></tr>
    <tr><td>3</td><td>Next hop: an instance, such as kade-proxy</td><td>**Zonal**</td><td>If zone a fails, the path through kade-proxy fails with it</td></tr>
    <tr><td>4</td><td>Next hop: an internal passthrough Network Load Balancer</td><td>Regional</td><td>Backends in two zones and health checks keep the path up</td></tr>
    <tr><td>5</td><td>Cloud Router and its dynamic routes</td><td>Regional</td><td>The routing mode decides whether its learned routes apply in its own region only or in every region (section 03)</td></tr>
  </tbody>
</Table>

Two rules follow:

- **One next hop VM is one zone.** For anything that matters, use a load balancer next hop (row 4), the same lesson as <Ch n="1.1" section="What an outage takes down">chapter 1.1</Ch>'s outage.
- **Keep the next hop near the traffic.** A tagged VM in asia-south1 would send its internet traffic to Singapore and only then out: slower, and billed as traffic between regions (<Ch n="1.1" section="Speed and price across zones and regions">chapter 1.1</Ch>). One proxy per region, each with its own tag, avoids the detour.
