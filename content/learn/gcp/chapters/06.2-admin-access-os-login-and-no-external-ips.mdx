<Box kind="problem" title="The problem">

Look at kade-prod's project metadata and there is a list of SSH public keys under `ssh-keys`. Some belong to the team. One belongs to a freelancer who worked on Kadé last year. Nobody removed it, and a key in project metadata works on **every** VM.

IAP from <Ch n="6.1">chapter 6.1</Ch> limits who can reach port 22. But anyone who can reach it and still holds an old private key can log in, and the logs only say that "someone used this key".

## The older way: SSH keys in metadata

<Recalls><Recall n="29">SSH keys</Recall></Recalls>

Without OS Login, a VM decides who may log in by a list of SSH **public keys** kept in metadata, either on the project (every VM) or on one VM. A small Google program on each VM, the **guest agent**, copies that list into the VM. Anyone who holds the matching **private key** can log in. Nothing asks whether that person should still have access.

<Figure wide hues={["amber", "teal"]} labels={{ amber: "The key list in project metadata", teal: "Kadé's VMs, each accepting every key" }} drawing={<FigKeys />}>
One list, copied to every VM. The freelancer's key is still on it, so the freelancer can still log in everywhere, and the VM's log names only the key.
</Figure>

The part most people miss is how the keys got there. When OS Login is off and you run `gcloud compute ssh` for the first time, gcloud creates a key pair on your laptop and **adds your public key to the project's metadata**, if you have permission to edit it. So every person who has ever SSHed in with gcloud has usually left a key behind that works on every VM.

## The better way: OS Login

<Term>OS Login</Term> is a Google service that ties SSH login to Google identities and IAM, instead of keys kept in metadata. Like IAP, it is nothing you install or run as a server. It has two halves:

- **At Google:** OS Login keeps a profile for each person: their Linux username, their user ID and their public SSH keys, all tied to their Google account. IAM records who may log in and who may use sudo.
- **On each VM:** small parts of Google's guest environment, already installed in Google's public images, connect Linux to that profile. They let sshd fetch a person's keys from Google, and let Linux know accounts such as `you_kade_lk` that appear in no local user file. Setting `enable-oslogin=TRUE` in metadata switches them on.

The difference from metadata keys is **when** access is decided. With metadata keys, it was decided once, when someone added a key, maybe a year ago. With OS Login, the VM asks at **every login**: whose key is this, and does IAM let that person in right now? It asks through its **metadata server**, `169.254.169.254`, a Google service that every VM reaches on its own host. So the check needs no internet access and no external IP, which matters for the rest of this chapter.

<Figure wide hues={["plum", "teal", "green"]} labels={{ plum: "Google's: OS Login, which holds your profile and asks IAM", teal: "kade-vpc and kade-db", green: "Your login" }} drawing={<FigOsLogin />}>
Your key lives on your OS Login profile, tied to you@kade.lk, not in the VM's metadata. Each login is checked against IAM at that moment, so removing a role ends access on every VM at once.
</Figure>

<Key title="Two role traps">

- **The VM's service account.** If the VM runs as a service account (all of Kadé's do after <Ch n="5.1">chapter 5.1</Ch>), the person also needs `roles/iam.serviceAccountUser` on that service account. The login role alone is not enough. Why is explained just below.
- **People outside the organization.** A user who is not part of `kade.lk`, like the freelancer, also needs `roles/compute.osLoginExternalUser`, granted at the organization level.

</Key>

### Why logging in needs the VM's service account

Logging in to a VM gives you more than a shell. It also gives you the VM's own Google identity:

- **A VM runs as a service account.** kade-db runs as `sa-kade-db`, and Google API calls from kade-db carry that service account's permissions.
- **Any program on the VM can use it.** The metadata server, `169.254.169.254`, hands the service account's token to whoever asks from inside the VM. It cannot tell the database apart from a person who has logged in.
- **So a login can borrow those permissions.** That is called **privilege escalation**: getting access your own roles never gave you.

<Figure wide hues={["plum", "teal"]} labels={{ plum: "Google's: the metadata server and Secret Manager", teal: "kade-vpc and kade-db" }} drawing={<FigBorrow />}>
dev2 has no Secret Manager access, but one command on kade-db runs as `sa-kade-db` and reads the database password.
</Figure>

Google closes this gap with one firm rule: nobody may use a service account's permissions unless IAM says they may act as it, which is what `roles/iam.serviceAccountUser` grants. Google checks it at every point where a service account could be borrowed:

<Table>
  <thead>
    <tr><th>#</th><th>A way to borrow `sa-kade-db`</th><th>Where Google checks `serviceAccountUser`</th></tr>
  </thead>
  <tbody>
    <tr><td>1</td><td>Create a new VM that runs as `sa-kade-db`, then log in to it</td><td>When you create the VM</td></tr>
    <tr><td>2</td><td>Deploy a Cloud Run service that runs as `sa-kade-db`</td><td>When you deploy (<Ch n="10">chapter 10</Ch>)</td></tr>
    <tr><td>3</td><td>Log in to kade-db, which already runs as `sa-kade-db`</td><td>**When you log in, by OS Login**</td></tr>
  </tbody>
</Table>

<Caption>Once you are inside the VM, nothing can check who you are any more, so the check has to happen at the door. With metadata keys there was no such check: Google only knew that some key matched, not who was logging in. OS Login knows the person, so it can apply the rule.</Caption>

Two habits follow:

- **Grant `serviceAccountUser` on each VM's own service account**, not on the project. On the project, the person could act as every service account in it.
- **Keep each service account's permissions small**, as <Ch n="5.1">chapter 5.1</Ch> did by giving each VM its own. Logging in to a VM always brings its permissions along.

<Note>

**`serviceAccountUser` is never enough on its own.** It only lifts the "you may not act as this service account" block. It always goes with the role for the action itself: an OS Login role to log in, `compute.instanceAdmin.v1` to create a VM that runs as the service account, `run.developer` to deploy Cloud Run with it. Getting the service account's token directly from your laptop, with `--impersonate-service-account`, is a different role again: `roles/iam.serviceAccountTokenCreator`.

</Note>

## Switching to OS Login safely

Do this **after** <Ch n="6.1">chapter 6.1</Ch>'s IAP change is proven, not at the same time. Changing both the access path and the login method at once makes it hard to tell which one broke if something does.

<Table>
  <thead>
    <tr><th>#</th><th>Step</th><th>Check</th></tr>
  </thead>
  <tbody>
    <tr><td>1</td><td>Grant the roles first: `compute.osAdminLogin` for you, `serviceAccountUser` on each VM's service account</td><td>The grants show in IAM</td></tr>
    <tr><td>2</td><td>Turn on OS Login for **one** VM: `enable-oslogin=TRUE` on kade-api-2</td><td>IAP SSH to kade-api-2 logs you in as `you_kade_lk`, and `sudo` works</td></tr>
    <tr><td>3</td><td>Turn it on for the project</td><td>SSH works on every VM</td></tr>
    <tr><td>4</td><td>Remove the old `ssh-keys` from project metadata</td><td>Nothing changes for anyone, because OS Login already ignores them. This is cleanup, and it removes the fallback if OS Login is ever turned off</td></tr>
    <tr><td>5</td><td>Later: require OS Login with an organization policy</td><td><Ch n="17">Chapter 17</Ch></td></tr>
  </tbody>
</Table>

<Note>

**VMs created by a managed instance group.** They read the same project metadata, so with `enable-oslogin=TRUE` set on the project, every VM the group creates already uses OS Login. Do not put `enable-oslogin` or `ssh-keys` in the instance template: a value there overrides the project for every future VM (<Ch n="12.2">chapter 12.2</Ch>).

</Note>

<Note>

**Automation.** Scripts and CI jobs that SSH to VMs need an identity too. With OS Login, give the job's service account the OS Login role, the same as a person. No shared key to rotate.

</Note>

## Removing a VM's external IP: the full picture

<Recalls><Recall n="10">NAT</Recall></Recalls>

Can a VM have no external IP and still do its job? Yes. Every kind of traffic a VM needs has its own path that does not use the VM's own public address. There are four, each from a different chapter:

<Figure wide hues={["plum", "teal", "green"]} labels={{ plum: "Google's network: IAP, the load balancer and Google APIs", teal: "kade-vpc, its VMs and Cloud NAT", green: "Traffic coming in" }} drawing={<FigNoip />} />

<Table>
  <thead>
    <tr><th>#</th><th>Without an external IP, the VM would be…</th><th>Fixed by</th><th>Chapter</th></tr>
  </thead>
  <tbody>
    <tr><td>1</td><td>Unreachable for admin work</td><td>IAP TCP forwarding</td><td className="whitespace-nowrap">6.1</td></tr>
    <tr><td>2</td><td>Unable to reach Google APIs (Cloud Storage, Secret Manager, Logging)</td><td>Private Google Access</td><td className="whitespace-nowrap">9</td></tr>
    <tr><td>3</td><td>Unable to reach the internet (apt, PayGate)</td><td>Cloud NAT in its region</td><td className="whitespace-nowrap">7</td></tr>
    <tr><td>4</td><td>Unreachable for the public (a website or an API)</td><td>An external load balancer</td><td className="whitespace-nowrap">11, 12</td></tr>
  </tbody>
</Table>

Path 4 is how a VM serves the public without a public address of its own, and it is the one most people ask about:

- **The public IP lives on the load balancer, not the VM.** Shoppers connect to `34.120.88.10`, which belongs to the load balancer's forwarding rule. The load balancer then connects to the VMs on their **internal** IPs, across Google's network (<Ch n="12.2">chapter 12.2</Ch> builds this for kade-media).
- **The firewall lets the app's port in from the load balancer's ranges only**: `35.191.0.0/16` and `130.211.0.0/22`, the same ranges its health checks use. Nobody else can reach port 8080.
- **Cloud NAT does not help here.** NAT is outbound only: it lets a VM start connections out, and it never accepts a new connection in. Inbound public traffic always needs a load balancer, or an external IP.
- **The VM sees the load balancer's address, not the shopper's.** The shopper's real IP arrives in a header (<Ch n="12.1" section="The real client IP">chapter 12.1</Ch>).

With all four paths in place, a VM does its whole job while nothing on the internet can start a connection to it directly. A VM becomes reachable from the internet in only two ways: an external IP of its own, or a place behind an external load balancer. Take away the first, and the only way in is the one Kadé builds on purpose (<Ch n="11">chapters 11</Ch> to 13). That makes **no external IP the strongest position a VM can be in**.

<Key title="It is ordered work, not a quick win">

For a VM that has an external IP today, the prerequisites must land first: Cloud NAT in the region, Private Google Access on the subnet, any database moved to a private path, and, for a VM that serves the public, a load balancer in front of it with its own public IP. Only then can the VM's IP come off. IAP is the one piece that can be done early and on its own, because it is what makes "no external IP" survivable for admin work. That is exactly why it came first in this course.

</Key>

## Back to Kadé

<Box kind="fixed" title="Fixed: SSH access is identity-only">

- **OS Login is on for the project.** You have `compute.osAdminLogin`; nobody else has a standing login role.
- **The old keys are gone.** The `ssh-keys` list in project metadata is removed, including the freelancer's. It had already stopped working the moment OS Login was turned on.
- **The freelancer's next visit** is three grants, all removable in one place: IAP tunnel on kade-worker (6.1 section 05, tab B), `compute.osLogin` on kade-worker, and `compute.osLoginExternalUser` at the organization.
- **Still open:** outgoing internet (<Ch n="7">chapter 7</Ch>) and Google APIs without the internet (<Ch n="9">chapter 9</Ch>). Kadé's VMs already have no external IPs; after those two chapters, they no longer need one for anything.

</Box>

## Commands in this chapter

Commands 1 to 3 are read-only. Commands 4 to 7 change the project.

<TryIt n={1} title="See SSH keys and OS Login settings in project metadata">

- **What it shows:** Project-wide metadata, including `ssh-keys` and `enable-oslogin`.
- **What to look for:** Keys whose owner you cannot name, and whether `enable-oslogin` is `TRUE`.

```sh
gcloud compute project-info describe \
  --format="yaml(commonInstanceMetadata.items)"
```

</TryIt>

<TryIt n={2} title="See one VM's own metadata">

- **What it shows:** Instance-level keys and settings, which override the project's.
- **What to look for:** `enable-oslogin=FALSE` on a single VM, which would switch it back to metadata keys.

```sh
gcloud compute instances describe kade-db --zone=asia-southeast1-b \
  --format="yaml(metadata.items)"
```

</TryIt>

<TryIt n={3} title="See your OS Login profile">

- **What it shows:** Your Linux username and the keys registered to your identity.
- **What to look for:** The username, e.g. `you_kade_lk`, which is what shows in the VM's logs.

```sh
gcloud compute os-login describe-profile
```

</TryIt>

<TryIt n={4} title="Grant OS Login with sudo (changes the project)">

- **What it shows:** Lets you log in to every VM as an admin.
- **What to look for:** Use `roles/compute.osLogin` instead for people who do not need sudo.

```sh
gcloud projects add-iam-policy-binding kade-prod \
  --member=user:you@kade.lk --role=roles/compute.osAdminLogin
```

</TryIt>

<TryIt n={5} title="Allow using a VM's service account (changes the project)">

- **What it shows:** The second role trap: needed to log in to a VM that runs as sa-kade-db.
- **What to look for:** Without it, OS Login refuses even with the login role.

```sh
gcloud iam service-accounts add-iam-policy-binding \
  sa-kade-db@kade-prod.iam.gserviceaccount.com \
  --member=user:you@kade.lk --role=roles/iam.serviceAccountUser
```

</TryIt>

<TryIt n={6} title="Turn on OS Login for one VM, then the project (changes the project)">

- **What it shows:** Steps 2 and 3 of section 04.
- **What to look for:** After the first line, test SSH to kade-api-2 before running the second.

```sh
gcloud compute instances add-metadata kade-api-2 --zone=asia-southeast1-b \
  --metadata=enable-oslogin=TRUE
gcloud compute project-info add-metadata --metadata=enable-oslogin=TRUE
```

</TryIt>

<TryIt n={7} title="Remove the old keys from project metadata (changes the project)">

- **What it shows:** Step 4 of section 04: cleanup of every project-wide SSH key.
- **What to look for:** `ssh-keys` gone from command 1. Save command 1's output first as a record.

```sh
gcloud compute project-info remove-metadata --keys=ssh-keys
```

</TryIt>
