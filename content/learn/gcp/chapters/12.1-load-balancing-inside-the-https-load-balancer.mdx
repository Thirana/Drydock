## The chain: five links

A proxy load balancer is a chain, and each link does one job. Click a link to see what it holds, Kadé's value, and the question to ask it when something breaks. Knowing which link to look at is half of any load balancer problem.

<LbChain />

### The target proxy: where the connection ends

The forwarding rule is only an address, `34.120.88.10:443`. It decides where a connection arrives, but something has to answer it, and the target proxy says how. It is not a machine you run, size or patch. It is a set of instructions that Google's front ends follow, at every edge location where a shopper can arrive (<Ch n="1.1">chapter 1.1</Ch>). For a regional load balancer, the Envoy proxies in your proxy-only subnet follow them instead (<Ch n="2">chapter 2</Ch> section 06).

The instructions come down to three steps. Answer the TCP handshake. Prove to the browser that this really is `kade.lk` by showing its certificate, then agree on encryption. Decrypt, and read the HTTP request. Only after the third step is there a host and a path for the URL map to read.

<Figure wide hues={["plum", "amber", "teal"]} labels={{ plum: "Google's front end, which runs the load balancer", amber: "The settings Kadé writes: target proxy, URL map, backend service", teal: "Kadé's service" }} drawing={<FigTargetProxy />}>
Two connections, not one. The shopper's connection ends at the target proxy. The backend only ever sees connection 2, which the front end opens once the URL map and backend service have chosen where the request goes (<Ch n="11">chapter 11</Ch> section 05).
</Figure>

Because the connection ends here, everything about the shopper's side of it is set here:

A load balancer has a target proxy exactly when it is a proxy. The kind of proxy decides how much it can read:

<Figure wide hues={["amber"]} labels={{ amber: "The target proxy: only proxy load balancers have one" }} drawing={<FigProxyKinds />}>
The same chain, three ways. Take away the URL map and the load balancer can no longer route by path. Take away the target proxy too and nothing ends the connection: the backends see the client's own address.
</Figure>

- **Target HTTPS proxy:** ends TCP and TLS, reads HTTP. Kadé's `kade-https-proxy`.
- **Target HTTP proxy:** ends TCP and reads HTTP, with no TLS. Kadé's `kade-http-proxy` exists only to answer port 80 with a redirect to HTTPS.
- **Target TCP proxy** and **target SSL proxy:** the proxy Network Load Balancer. The SSL one ends TLS too, but neither reads HTTP, so they point straight at one backend service, with no URL map.
- **No target proxy:** a passthrough Network Load Balancer. Its forwarding rule points straight at a backend service.

<Key title="When the problem is at the target proxy">

A certificate error in the browser, or a TLS handshake that fails, happens at the target proxy. The connection never got as far as the URL map, so no backend saw it and its logs show nothing. Check the proxy's certificates and SSL policy first (Try it 1 and 6 below).

</Key>

## The URL map: where each request goes

The URL map can only route by host and path because the target proxy has already ended the connection and decrypted it. It works in two steps: a **host rule** picks a path matcher by hostname, then the **path matcher** picks a backend by the longest matching path. Anything that matches nothing goes to the default backend.

## Backend types

A backend service points at one or more **backends**, the things that actually answer requests. What matters first is **where the backend runs**:

Kadé's backend bucket `kade-static` serves `www.kade.lk` and `/images/`.

<Key title="The serverless NEG is the one to remember, and it is different">

It is the bridge between a load balancer and Cloud Run: it gives a Cloud Run service a custom domain, a certificate, Cloud Armor and Cloud CDN, and with the right ingress setting (<Ch n="10">chapter 10</Ch>) it becomes the only way in. Three things work differently from VM backends:

- **No health checks.** Cloud Run manages its own instances; the load balancer does not probe them. (Outlier detection can still stop sending traffic to a region that keeps returning errors.)
- **No backend service timeout.** The request timeout is set on the Cloud Run service itself.
- **No firewall rule for Google's ranges.** Cloud Run is not in your VPC, so there is nothing for `kade-allow-lb` to allow.

</Key>

**Balancing mode** is the one that decides where traffic goes. Each group has a target, and a group at its target counts as full:

**Session affinity** is needed only when a backend keeps a shopper's state in its own memory:

<Figure wide hues={["teal", "green"]} drawing={<FigAffinity />}>

## Cloud Armor: the WAF

Cloud Armor is attached to a **backend service** (link 4 of the chain). It looks at each request at Google's front end, before it reaches your backends, and allows, denies, or rate-limits it. Unlike the VPC firewall, it sees the real client IP and the request itself (<Ch n="5.2">chapter 5.2</Ch>).

## Cloud CDN

Cloud CDN caches responses at Google's edge locations, so repeated requests are answered near the user without reaching the backend. It is turned on per **backend service or backend bucket**, the same place Cloud Armor attaches. Kadé turns it on for `kade-static`, with the cache mode `CACHE_ALL_STATIC`: static files such as product images are cached, and nothing from the API is.

<Caption>What gets cached and for how long, the cache key, replacing a cached file and reading hits in the logs are all in <Ch n="12.4">chapter 12.4</Ch>. <Ch n="13">Chapter 13</Ch> adds Cloudflare's cache in front.</Caption>

## Logs: who answered?

Request logging is turned on per backend service, with a sample rate. Each log line has a `statusDetails` field that says who produced the response, which settles most "is it the load balancer or the app?" arguments:

<Figure wide hues={["plum", "amber", "teal", "green"]} labels={{ amber: "Cloud Armor", teal: "Your backend" }} drawing={<FigWhoAnswered />}>

A `500` with `response_sent_by_backend` is an app bug. `failed_to_pick_backend` sends you to the health checks (section 04). `denied_by_security_policy` comes with `enforcedSecurityPolicy`, which names the rule (<Ch n="12.3">chapter 12.3</Ch>).

</Figure>

## Back to Kadé

<Box kind="fixed" title="Fixed: the four problems at the top">

- **Unhealthy backends.** The cause was a firewall clean-up that removed the rule for `35.191.0.0/16` (hcex tab A). Today the backend is a serverless NEG with no health checks, and when Kadé uses VMs again they get an HTTP health check on `/healthz` and a dedicated firewall rule.
- **Client IP.** The API reads the second-to-last entry of `X-Forwarded-For`, the address Google's front end saw, and never the first (section 06). <Ch n="13">Chapter 13</Ch> changes this when Cloudflare is added.
- **Certificate.** Replaced with a Google-managed certificate through Certificate Manager with DNS authorization, for `kade.lk` and `*.kade.lk`, on `kade-cert-map`. It renews itself, and it will keep working behind Cloudflare. SSL policy `kade-tls`: MODERN, TLS 1.2 minimum.
- **WAF coverage.** `kade-edge-policy` is attached to `kade-api-backend`, the only backend service, and kade-api's ingress is `internal-and-cloud-load-balancing` (<Ch n="10">chapter 10</Ch>), so there is no way around it. Backend buckets can only take an edge security policy, so `kade-static` gets `kade-static-edge` (rate limits and country rules).

## Commands in this chapter

Commands 1 to 7 are read-only. Commands 8 to 10 change the project.

<TryIt n={1} title="Follow the chain from the IP">

- **What it shows:** The forwarding rule's target proxy, then that proxy's URL map and certificate setup.
- **What to look for:** Which proxy each forwarding rule uses, and whether the HTTPS proxy has a certificate map and an SSL policy.

```sh
gcloud compute forwarding-rules describe kade-https-rule --global --format="value(target)"
gcloud compute target-https-proxies describe kade-https-proxy \
  --format="yaml(urlMap,certificateMap,sslCertificates,sslPolicy)"
```

</TryIt>

<TryIt n={2} title="See how the URL map routes">

- **What it shows:** Host rules, path matchers and the default service.
- **What to look for:** Every hostname you serve has a host rule, and the default service is what you expect for unknown hosts.

```sh
gcloud compute url-maps describe kade-url-map --format="yaml(defaultService,hostRules,pathMatchers)"
```

</TryIt>

<TryIt n={3} title="Check a backend service's protection and settings">

- **What it shows:** Cloud Armor policy, CDN, logging, timeout, affinity and backends.
- **What to look for:** An empty `securityPolicy` means no WAF on this backend service.

```sh
gcloud compute backend-services describe kade-api-backend --global \
  --format="yaml(securityPolicy,enableCDN,logConfig,timeoutSec,sessionAffinity,backends)"
```

</TryIt>

<TryIt n={4} title="Find backend services with no Cloud Armor policy">

- **What it shows:** Every backend service and its security policy, in one table.
- **What to look for:** A blank policy on anything public-facing. This is the "WAF on some load balancers but not others" check.

```sh
gcloud compute backend-services list \
  --format="table(name,loadBalancingScheme,securityPolicy.basename())"
```

</TryIt>

<TryIt n={5} title="See backend health (VM or zonal NEG backends)">

- **What it shows:** Each backend instance and whether the health check passes.
- **What to look for:** `UNHEALTHY` while the app works means the probe path: firewall rule, port, or health check path.

```sh
gcloud compute backend-services get-health kade-api-backend --global
```

</TryIt>

<TryIt n={6} title="Check certificate status">

- **What it shows:** Each Certificate Manager certificate, its domains and its state.
- **What to look for:** `ACTIVE`. `PROVISIONING` for a long time usually means the DNS authorization record is missing.

```sh
gcloud certificate-manager certificates list \
  --format="table(name,sanDnsnames.list(),managed.state,expireTime)"
```

</TryIt>

<TryIt n={7} title="Read load balancer logs for errors">

- **What it shows:** Recent requests with status 5xx, and who produced each response.
- **What to look for:** The `statusDetails` value (section 10).

```sh
gcloud logging read \
  'resource.type="http_load_balancer" AND httpRequest.status>=500' \
  --freshness=1h --limit=20 \
  --format="table(timestamp,httpRequest.status,jsonPayload.statusDetails,httpRequest.requestUrl)"
```

</TryIt>

<TryIt n={8} title="Attach a Cloud Armor policy to a backend service (changes the project)">

- **What it shows:** Puts kade-edge-policy in front of kade-api-backend.
- **What to look for:** The policy name in command 4. Repeat for every public backend service.

```sh
gcloud compute backend-services update kade-api-backend --global \
  --security-policy=kade-edge-policy
```

</TryIt>

<TryIt n={9} title="Add a WAF rule in preview mode first (changes the project)">

- **What it shows:** A SQL injection rule that only logs what it would block.
- **What to look for:** Matches in the logs with `previewSecurityPolicy`. When there are no false positives, update the rule with `--no-preview`.

```sh
gcloud compute security-policies rules create 1000 --security-policy=kade-edge-policy \
  --expression="evaluatePreconfiguredWaf('sqli-v33-stable')" --action=deny-403 --preview
```

</TryIt>

<TryIt n={10} title="Require modern TLS (changes the project)">

- **What it shows:** Creates the SSL policy and attaches it to the HTTPS proxy.
- **What to look for:** `sslPolicy` set in command 1. Very old clients that only speak TLS 1.0 can no longer connect.

```sh
gcloud compute ssl-policies create kade-tls --profile=MODERN --min-tls-version=1.2
gcloud compute target-https-proxies update kade-https-proxy --ssl-policy=kade-tls
```

</TryIt>
