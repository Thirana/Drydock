## Why fixes drift back, and the two answers

A fix made by hand stays fixed only as long as nobody with access changes it. There are two kinds of answer, and a good setup uses both:

## The resource hierarchy: where rules are set

Every GCP resource sits in a project, projects sit in folders, folders in the organization. IAM permissions and policies set high up are **inherited** by everything below. That is what makes governance possible: set a rule once on the folder, and every current and future project in it follows (<Ch n="5.2">chapter 5.2</Ch> used this for hierarchical firewall policies).

<GovHier />

## Organization policies: how they work

An organization policy sets a **constraint** on a node of the hierarchy: "VMs in here may not have external IPs", "Cloud SQL in here may not have a public IP". It does not grant or remove anyone's access. It limits what **anyone** can create or configure, including Owners.

<Table>
  <thead>
    <tr><th>#</th><th>Kind of constraint</th><th>Settings</th><th>Example</th></tr>
  </thead>
  <tbody>
    <tr><td>1</td><td>**Boolean**</td><td>Enforced or not</td><td>`compute.skipDefaultNetworkCreation`: new projects get no default network</td></tr>
    <tr><td>2</td><td>**List**</td><td>Allowed values, denied values, or deny all</td><td>`run.allowedIngress`: only `internal` and `internal-and-cloud-load-balancing`</td></tr>
    <tr><td>3</td><td>**Custom**</td><td>Your own condition on a resource's fields, for supported resource types</td><td>For rules no built-in constraint expresses</td></tr>
  </tbody>
</Table>

Four behaviours decide whether a policy does what you expect. Each tab shows one:

<OrgPolEx />

<Key title="Policies are not retroactive">

Turning on "no external IPs" stops **new** ones. A VM that already has an external IP keeps it. Before enforcing a policy, find what already breaks it (section 08, Cloud Asset Inventory), fix those, and use dry run to see what would be refused. Otherwise you get a false sense of safety, or a surprise outage when an existing resource is next updated.

</Key>

## IAM for the network: who can change what

Organization policies limit what can exist. IAM decides who can change the things that are allowed. The basic roles are the problem:

<Table>
  <thead>
    <tr><th>#</th><th>Role</th><th>Can change the network?</th><th>Use</th></tr>
  </thead>
  <tbody>
    <tr><td>1</td><td>`roles/owner`</td><td><St k="bad">everything</St>, including IAM itself</td><td>One or two break-glass accounts, not daily work</td></tr>
    <tr><td>2</td><td>`roles/editor`</td><td><St k="bad">almost everything</St>: firewall rules, routes, IPs</td><td>Avoid. It is the usual way "a developer opened port 22" happens</td></tr>
    <tr><td>3</td><td>`roles/compute.networkAdmin`</td><td>Networks, subnets, routes, load balancers, NAT, VPN. **Not** firewall rules or certificates</td><td>Whoever builds the network</td></tr>
    <tr><td>4</td><td>`roles/compute.securityAdmin`</td><td>Firewall rules, firewall policies, SSL certificates and policies</td><td>Whoever owns security. Kept separate on purpose</td></tr>
    <tr><td>5</td><td>`roles/compute.networkViewer`</td><td>Read only</td><td>Developers who need to see, not change</td></tr>
    <tr><td>6</td><td>`roles/compute.networkUser`</td><td>Use a (shared) subnet when creating resources</td><td>Service projects in a Shared VPC (<Ch n="14">chapter 14</Ch>)</td></tr>
    <tr><td>7</td><td>`roles/dns.admin`, `roles/compute.loadBalancerAdmin`</td><td>Only their own area</td><td>Narrow jobs</td></tr>
  </tbody>
</Table>

<Caption>Network Admin and Security Admin are split so that the person who builds a path is not automatically the person who opens the firewall on it. In a one-person team both land on the same person, but the habit of using narrow roles still keeps everyone else out.</Caption>

## VPC Service Controls: a perimeter around Google APIs

Firewall rules protect traffic to your VMs. They cannot protect **Google APIs** such as Cloud Storage or BigQuery: those are reached over Google's public endpoints, and IAM alone decides who can call them. If credentials leak, the attacker can download Kadé's data from anywhere. **VPC Service Controls** draws a perimeter around projects, so their protected APIs only answer requests from inside the perimeter, and data can only be copied to projects inside it.

<VpcScEx />

<Table>
  <thead>
    <tr><th>#</th><th>Piece</th><th>Job</th></tr>
  </thead>
  <tbody>
    <tr><td>1</td><td>Service perimeter</td><td>A set of projects and the APIs protected for them</td></tr>
    <tr><td>2</td><td>Access level</td><td>A rule for letting in requests from outside: the office IP range, or company-managed devices</td></tr>
    <tr><td>3</td><td>Ingress and egress rules</td><td>Narrow exceptions: "this outside service account may read this bucket"</td></tr>
    <tr><td>4</td><td>`restricted.googleapis.com`</td><td>The private API addresses that only serve perimeter-supported APIs (<Ch n="9">chapter 9</Ch>)</td></tr>
    <tr><td>5</td><td>Dry-run perimeter</td><td>Logs what would be blocked without blocking it. Always run it for a few weeks first</td></tr>
  </tbody>
</Table>

<Caption>VPC Service Controls adds work and breaks things that are not planned for (third-party tools reading your buckets, a CI system outside GCP). It earns its place when the data is sensitive: payments, personal data. Kadé starts with a dry-run perimeter around kade-prod.</Caption>

## The network written down: infrastructure as code

The strongest answer to "what should the network look like?" is a file. With Terraform (or a similar tool), the network from this course is described in code, kept in Git, reviewed before it changes, and applied by a CI job. A console change then shows up as **drift**: the next plan says "the real firewall differs from the code".

<IacFlow />

<Table>
  <thead>
    <tr><th>#</th><th>Rule</th><th>Why</th></tr>
  </thead>
  <tbody>
    <tr><td>1</td><td>Only the CI service account holds network write roles in kade-prod</td><td>People change the network by changing code, which gets reviewed</td></tr>
    <tr><td>2</td><td>Humans keep Network Viewer, plus a break-glass group for emergencies</td><td>Incidents still need hands; every use of break-glass is visible in the audit log</td></tr>
    <tr><td>3</td><td>A scheduled plan (daily) reports drift</td><td>Catches changes made outside the pipeline</td></tr>
    <tr><td>4</td><td>Start by importing what exists</td><td>Rewriting a working network from scratch is a risk of its own; import, then improve</td></tr>
  </tbody>
</Table>

<Caption>Infrastructure as code is a subject of its own. For this course, the point is the governance one: a written, reviewed description of the network is what turns "is this right?" from memory into a diff.</Caption>

## Commands in this chapter

Commands 1 to 5 are read-only. Commands 6 to 8 change the organization; run them with the organization or folder ID, after dry run.

<TryIt n={1} title="What policy actually applies to a project?">

- **What it shows:** The effective policy for one constraint on kade-prod, after inheritance and merging.
- **What to look for:** `enforce: true` or the allowed and denied values you expect. If it is empty, nothing above sets it.

```sh
gcloud org-policies describe compute.vmExternalIpAccess --project=kade-prod --effective
```

</TryIt>

<TryIt n={2} title="List the policies set on the folder">

- **What it shows:** Every constraint with a policy set directly on the production folder.
- **What to look for:** The constraints from section 11's table.

```sh
gcloud org-policies list --folder=FOLDER_ID
```

</TryIt>

<TryIt n={3} title="Find every external IP in the organization">

- **What it shows:** Reserved and in-use external addresses across all projects.
- **What to look for:** Anything besides the load balancer and NAT IPs. Fix these before enforcing `vmExternalIpAccess`.

```sh
gcloud asset search-all-resources --scope=organizations/ORG_ID \
  --asset-types=compute.googleapis.com/Address --query="addressType:EXTERNAL" \
  --format="table(displayName,project,location,additionalAttributes.address)"
```

</TryIt>

<TryIt n={4} title="Who holds Owner or Editor?">

- **What it shows:** Every IAM binding granting the basic roles, anywhere in the organization.
- **What to look for:** Individual users and former contractors. The goal is two break-glass Owners and no Editors.

```sh
gcloud asset search-all-iam-policies --scope=organizations/ORG_ID \
  --query="policy:(roles/owner OR roles/editor)" --format="table(resource,policy.bindings.role,policy.bindings.members)"
```

</TryIt>

<TryIt n={5} title="Who can change firewall rules in kade-prod?">

- **What it shows:** Every identity that holds the permission to update firewall rules, and through which role and level.
- **What to look for:** Only the platform group and the CI service account.

```sh
gcloud asset analyze-iam-policy --organization=ORG_ID \
  --full-resource-name=//cloudresourcemanager.googleapis.com/projects/kade-prod \
  --permissions=compute.firewalls.update
```

</TryIt>

<TryIt n={6} title="Block external IPs on VMs in the folder, dry run first (changes the organization)">

- **What it shows:** A policy file with a dry-run spec only: violations are logged, nothing is blocked. Move the rules to `spec` to enforce.
- **What to look for:** Dry-run violations in the audit logs for a week; zero means it is safe to enforce. Dry run is not available for every constraint; where it is not, preview with the Policy Simulator in the console, and fix what command 3 found first.

```sh
cat > no-external-ip.yaml <<'EOF'
name: folders/FOLDER_ID/policies/compute.vmExternalIpAccess
dryRunSpec:
  rules:
  - denyAll: true
EOF
gcloud org-policies set-policy no-external-ip.yaml
```

</TryIt>

<TryIt n={7} title="Require OS Login and skip default networks, organization-wide (changes the organization)">

- **What it shows:** Two boolean constraints enforced on the organization.
- **What to look for:** Command 1 on any project shows `enforce: true`. A new test project has no default network.

```sh
gcloud org-policies set-policy require-oslogin.yaml        # constraints/compute.requireOsLogin, enforce: true
gcloud org-policies set-policy skip-default-network.yaml   # constraints/compute.skipDefaultNetworkCreation, enforce: true
```

</TryIt>

<TryIt n={8} title="Alert on network changes (changes the project)">

- **What it shows:** A log-based metric counting changes to firewall rules, routes, addresses and security policies, for an alert to watch (<Ch n="16.2">chapter 16.2</Ch>).
- **What to look for:** The counter rising when you change a test rule; the alert's notification arriving.

```sh
gcloud logging metrics create kade_network_changes \
  --description="Changes to firewall rules, routes, addresses, security policies" \
  --log-filter='logName:"cloudaudit.googleapis.com%2Factivity" AND
    (protoPayload.methodName:("compute.firewalls." OR "compute.routes." OR
     "compute.addresses." OR "compute.securityPolicies."))'
```

</TryIt>
