## What ARP does

<Term>ARP</Term> (Address Resolution Protocol) has one job: give it an IP address on your local network, and it returns the MAC address of the interface that holds that IP.

You already know a lookup like this. DNS turns a name into an IP. ARP turns an IP into a MAC:

  <thead>
    <tr><th></th><th>DNS (<Ch n="1">chapter 1</Ch>)</th><th>ARP</th></tr>

  <tbody>
    <tr><td>Input</td><td><Mono>api.kade.lk</Mono></td><td><Mono>172.16.1.20</Mono></td></tr>
    <tr><td>Output</td><td><Mono>34.87.120.15</Mono></td><td><Mono>30:05:5c:8a:12:e0</Mono></td></tr>

    <tr><td>Result kept for</td><td>The record's TTL</td><td>Seconds to minutes (depends on the OS)</td></tr>
  </tbody>
</Table>

The PC already knows the printer's IP (the print setup stores it, just as your frontend knows the backend's address after DNS). First, the mask check from <Ch n="4">chapter 4</Ch>: 172.16.1.10 AND mask = 172.16.1.0, and 172.16.1.20 AND mask = 172.16.1.0. Same network, so the PC can deliver directly. But to build the frame, it needs the printer's MAC.

## Request and reply

<ArpFan target="op" />

1. **Request, sent as a broadcast.** The PC sends a frame to `ff:ff:ff:ff:ff:ff`, the broadcast MAC (<Ch n="7">chapter 7</Ch>). The switch copies it to every port, so every device on the network gets it. It asks: "Who has 172.16.1.20? Tell 172.16.1.10."
1. **Everyone checks.** Each device compares 172.16.1.20 with its own IP. The manager laptop and the router do not match, so they ignore it.
1. **Only the owner replies, and only to the PC.** The printer sends "172.16.1.20 is at 30:05:5c:8a:12:e0" straight back to the PC's MAC. The reply is unicast, not a broadcast.

## What is inside an ARP message

Both messages have the same four fields. Only the values change:

  <thead>
    <tr><th>Field</th><th>Request</th><th>Reply</th></tr>

    <tr><td>Frame destination</td><td><Mono>ff:ff:ff:ff:ff:ff <Sub>everyone</Sub></Mono></td><td><Mono>3c:7c:3f:10:22:01 <Sub>only the PC</Sub></Mono></td></tr>
    <tr><td>Sender MAC</td><td><Mono>3c:7c:3f:10:22:01</Mono></td><td><Mono>30:05:5c:8a:12:e0 <Sub>the answer</Sub></Mono></td></tr>

    <tr><td>Target MAC</td><td><Mono>00:00:00:00:00:00 <Sub>unknown, that's the question</Sub></Mono></td><td><Mono>3c:7c:3f:10:22:01</Mono></td></tr>

  </tbody>
</Table>

<Caption>ARP is carried directly in a frame. There is no IP packet around it, which is why it can work before a device knows anyone's MAC.</Caption>

## The ARP table (cache)

Broadcasting before every single frame would waste the whole network's time. So every device keeps an <Term>ARP table</Term>: a small cache of IP → MAC pairs it has learned. The PC's table before and after:

<Cols n={2}>

<Col title="Before">

<Mono>172.16.1.1 → e4:8d:8c:00:01:01</Mono>

learned earlier, when the PC first went online

</Col>

<Col title="After">

<Mono>172.16.1.1 → e4:8d:8c:00:01:01<br />172.16.1.20 → 30:05:5c:8a:12:e0</Mono>

the next print job skips the broadcast

</Col>

</Cols>

- **Entries expire.** After a while (seconds to minutes, depending on the OS) an unused entry is dropped or rechecked. If the printer is replaced, its new MAC is picked up on the next lookup.
- **The target learns too.** The request already contained the PC's IP and MAC, so the printer saves 172.16.1.10 → 3c:7c:3f:10:22:01. When it replies, it does not need to ask.
- **A small correction to the notes:** a device does not find its own MAC in the ARP table. It knows its own addresses from its interface settings. The table holds other devices.

## When the target is on another network

Now the PC loads an order from kade-api (34.87.120.15). The mask check fails: 34.87.120.0 is not 172.16.1.0. So the PC must send to its default gateway, 172.16.1.1 (it got that from DHCP, <Ch n="5">chapter 5</Ch>). It runs ARP for the **gateway's** IP, and this time the router replies:

<ArpFan target="gw" />

The frame then goes out with the router's MAC and kade-api's IP, just as in <Ch n="1">chapters 1</Ch> and <Ch n="5">5</Ch>:

<Table>
  <tbody>
    <tr><td>**Destination MAC**</td><td><Mono>e4:8d:8c:00:01:01</Mono></td><td>router eth1, from ARP</td></tr>
    <tr><td>**Destination IP**</td><td><Mono>34.87.120.15</Mono></td><td>kade-api, unchanged</td></tr>
  </tbody>
</Table>

<Key title="ARP never leaves the local network">

Broadcasts stop at the router. The PC never learns kade-api's MAC, and never needs it. At each later hop, the next router runs its own ARP on its own local link.

</Key>

## ARP trusts everyone

ARP has no checks. Any device can send a reply, even one nobody asked for, and most devices will cache it. An attacker on the staff network could send "172.16.1.1 is at _my_ MAC". The PC would then send all its internet traffic to the attacker first. This is called <Term>ARP spoofing</Term>, and it is one reason public WiFi is risky and why HTTPS (TLS) matters even on a "private" network. Managed switches can block it with a feature called dynamic ARP inspection.

<Note>

**In GCP:** a VPC has no broadcast at all. VMs still send ARP requests, but the VPC's software network answers them itself. So ARP spoofing between VMs does not work there, and kade-api always reaches its gateway 10.10.1.1 through Google's network.

</Note>

- **Runs on:** macOS / Linux / Windows · Linux also: ip neigh

```sh
arp -a
```

<TryIt n={2} title="Delete one entry">

```sh
sudo arp -d 192.168.1.1
```
