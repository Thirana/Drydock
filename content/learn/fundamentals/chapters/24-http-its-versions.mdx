<Part n="A">The protocol</Part>

## Request and response, no memory

<Term>HTTP</Term> (HyperText Transfer Protocol) is a request/response protocol: the client sends a request, the server returns one response. It is <Term>stateless</Term>: each request stands alone, and the server does not remember the previous one. That is why cookies and tokens exist, to carry "who you are" on every request (section 6).

## What a request and a response contain

Both have the same shape: a start line, headers, a blank line, and an optional body. Here is the Kadé app placing an order:

<Cols n={2}>

<Col title="Request">

```text
POST /orders HTTP/1.1
Host: api.kade.lk
Authorization: Bearer eyJhbGci…
Content-Type: application/json
Content-Length: 58

{"items":[{"sku":"RICE-5KG","qty":2}],"slot":"evening"}
```

Request line: method + path + version. Then headers, a blank line, the body.

</Col>

<Col title="Response">

```text
HTTP/1.1 201 Created
Content-Type: application/json
Location: /orders/1042
Cache-Control: no-store
Content-Length: 41

{"id":1042,"status":"confirmed","total":…}
```

Status line: version + status code + reason. Then headers, a blank line, the body.

</Col>

</Cols>

The body's size is given by `Content-Length`. When the server does not know the size in advance (streaming a CSV export, <Ch n="19">chapter 19</Ch>), it uses `Transfer-Encoding: chunked` in HTTP/1.1 and sends the body in pieces, each with its own length.

## Methods

The method states the request's intent. Two properties decide what is safe to **retry** automatically, which matters a lot when connections drop (<Ch n="21">chapter 21</Ch>):

<Table>
  <thead>
    <tr><th>#</th><th>Method</th><th>Intent</th><th>Kadé example</th><th>Safe?</th><th>Idempotent?</th></tr>
  </thead>
  <tbody>
    <tr><td>1</td><td>**GET**</td><td>Read something</td><td>`GET /orders/1042`</td><td>yes</td><td>yes</td></tr>
    <tr><td>2</td><td>**POST**</td><td>Create, or run an action</td><td>`POST /orders`</td><td>no</td><td>no</td></tr>
    <tr><td>3</td><td>**PUT**</td><td>Replace a resource entirely</td><td>`PUT /users/me/address`</td><td>no</td><td>yes</td></tr>
    <tr><td>4</td><td>**PATCH**</td><td>Change part of a resource</td><td>`PATCH /orders/1042 {"slot":"morning"}`</td><td>no</td><td>not guaranteed</td></tr>
    <tr><td>5</td><td>**DELETE**</td><td>Remove</td><td>`DELETE /cart/items/9`</td><td>no</td><td>yes</td></tr>
    <tr><td>6</td><td>HEAD</td><td>Like GET, headers only</td><td>checking a file's size</td><td>yes</td><td>yes</td></tr>
    <tr><td>7</td><td>OPTIONS</td><td>Ask what is allowed</td><td>the browser's CORS "preflight" before a cross-site call</td><td>yes</td><td>yes</td></tr>
  </tbody>
</Table>

<Caption>**Safe** = changes nothing on the server. **Idempotent** = doing it twice has the same effect as once. If a POST /orders times out, retrying it might create two orders. That is why payment APIs like PayGate accept an **idempotency key** header: the same key twice means "same request", and the server does not repeat it.</Caption>

## Headers, and remembering who you are

Headers carry metadata. The ones you meet daily:

<Table>
  <tbody>

    <tr><td><Mono>Content-Type / Accept</Mono></td><td>What the body is / what the client wants back (application/json, text/html …)</td></tr>
    <tr><td><Mono>Authorization</Mono></td><td>Credentials, usually `Bearer <token>`</td></tr>
    <tr><td><Mono>Cookie / Set-Cookie</Mono></td><td>The server sets a cookie; the browser sends it back on every later request</td></tr>
    <tr><td><Mono>Cache-Control, ETag</Mono></td><td>How long a response may be reused (section 7)</td></tr>
    <tr><td><Mono>Content-Encoding</Mono></td><td>Compression: gzip or br (Brotli). JSON often shrinks to a fifth.</td></tr>

  </tbody>
</Table>

Because HTTP is stateless, identity travels with every request, in one of two ways:

<Cols n={2}>

<Col title="Cookies">

Set-Cookie: sid=8f2a91c; HttpOnly; Secure; SameSite=Lax; Max-Age=86400

The browser stores it and sends `Cookie: sid=8f2a91c` automatically. **HttpOnly**: JavaScript cannot read it. **Secure**: HTTPS only. **SameSite**: not sent on most cross-site requests (blocks CSRF).

</Col>

<Col title="Tokens">

Authorization: Bearer eyJhbGciOi…

The app stores the token and adds the header itself. Common for mobile apps and APIs. Often a JWT: signed data the server can check without a database lookup.

</Col>

</Cols>

## Caching in one minute

`Cache-Control: max-age=86400` on a product image lets the browser (and any CDN) reuse it for a day without asking. When it expires, the browser asks again with `If-None-Match: "a1b2"` (the `ETag` it got before). If nothing changed, kade-api answers **304 Not Modified** with no body. `Cache-Control: no-store` on order details means "never keep this". Caching skips whole requests, which beats any protocol speed-up.

## Same meaning, better delivery

Every version keeps the same methods, status codes and headers. Only the way messages are carried changes:

<Table>
  <thead>
    <tr><th>#</th><th>Version</th><th>Year</th><th>Carried as</th><th>Connections</th><th>Transport</th></tr>
  </thead>
  <tbody>
    <tr><td>1</td><td>HTTP/1.0</td><td>1996</td><td>text</td><td>a new TCP connection for every request</td><td>TCP</td></tr>
    <tr><td>2</td><td>HTTP/1.1</td><td>1997</td><td>text</td><td>reused (keep-alive); one request at a time each</td><td>TCP</td></tr>
    <tr><td>3</td><td>HTTP/2</td><td>2015</td><td>binary frames</td><td>one connection, many streams at once</td><td>TCP (+ TLS)</td></tr>
    <tr><td>4</td><td>HTTP/3</td><td>2022</td><td>binary frames</td><td>one connection, fully independent streams</td><td>QUIC over UDP (TLS 1.3 built in)</td></tr>
  </tbody>
</Table>

## HTTP/1.1: keep-alive and head-of-line blocking

HTTP/1.1 kept connections open so they could be reused (**keep-alive**, <Ch n="21">chapter 21</Ch>), saving a handshake per request. But on one connection, requests are answered **one at a time, in order**: a slow response blocks everything behind it. This is <Term>head-of-line blocking</Term> at the HTTP level.

Browsers worked around it by opening up to **6 connections per host**, each paying its own TCP and TLS handshake and slow start (<Ch n="20">chapter 20</Ch>). Sites even split assets across several host names to get more connections ("domain sharding"). An idea to send several requests without waiting (pipelining) existed, but was too buggy and is not used.

## HTTP/2: many streams on one connection

HTTP/2 introduced <Term>multiplexing</Term>: many requests and responses share one connection as independent **streams**, cut into small binary **frames** and interleaved. Nothing waits in line at the HTTP level.

<Segments label="one TCP connection, frames from three streams interleaved">
  <Seg w={1} hue="plum">HEADERS s1</Seg>
  <Seg w={1} hue="amber">HEADERS s3</Seg>
  <Seg w={1} hue="plum">DATA s1</Seg>
  <Seg w={1} hue="green">HEADERS s5</Seg>
  <Seg w={1} hue="amber">DATA s3</Seg>
  <Seg w={1} hue="green">DATA s5</Seg>
  <Seg w={1} hue="plum">DATA s1</Seg>
  <Seg w={1} hue="amber">DATA s3 end</Seg>
</Segments>

<Caption>s1 = the page's CSS, s3 = a script, s5 = a product image. Each frame carries its stream number, so the receiver sorts them back out.</Caption>

- **Binary, not text:** faster and less error-prone to parse.
- **Header compression (HPACK):** headers repeat on every request (cookies, user agent). HPACK sends them once and then refers to them by number.
- **Per-stream flow control and priorities:** the same idea as <Ch n="19">chapter 19</Ch>, per stream.
- **Server push** (sending files before they are asked for) was part of HTTP/2 but proved unhelpful, and browsers have removed it.

## The problem HTTP/2 could not fix

HTTP/2 still runs on TCP, and TCP delivers **one ordered byte stream** (<Ch n="17">chapter 17</Ch>). If a single packet is lost, TCP holds back **everything** behind it until the resend arrives, including frames of streams that had nothing to do with the lost packet. HTTP/2 removed head-of-line blocking at the HTTP level but not at the TCP level. On lossy mobile networks, it can even do worse than HTTP/1.1's six connections, where one loss stalls only one of them.

## HTTP/3 on QUIC

HTTP/3 runs on <Term>QUIC</Term>, a transport built on UDP (<Ch n="14">chapter 14</Ch>) that does TCP's job itself, differently:

<Table>
  <thead>
    <tr><th>#</th><th>Feature</th><th>What it gives</th></tr>
  </thead>
  <tbody>
    <tr><td>1</td><td>Independent streams</td><td>Each stream has its own ordering. A lost packet delays only the stream it belonged to.</td></tr>
    <tr><td>2</td><td>TLS 1.3 built in</td><td>Transport and encryption handshakes are one: a new connection is ready in 1 round trip instead of 2 (<Ch n="25">chapter 25</Ch>). A returning client can even send data in the first flight ("0-RTT").</td></tr>
    <tr><td>3</td><td>Connection IDs</td><td>A connection is identified by an ID, not by the four addresses and ports. When the delivery rider's phone moves from WiFi to mobile data (new IP), the connection keeps going instead of breaking.</td></tr>
    <tr><td>4</td><td>Encrypted transport headers</td><td>Even packet numbers are encrypted, so middleboxes cannot interfere with it the way they sometimes do with TCP.</td></tr>
    <tr><td>5</td><td>QPACK</td><td>Header compression that works with out-of-order streams</td></tr>
  </tbody>
</Table>

<Caption>Browsers learn a server speaks HTTP/3 from an `Alt-Svc` header on an earlier response, or from a DNS HTTPS record. They race QUIC against TCP and fall back to HTTP/2 if UDP 443 is blocked, as it is on some office networks.</Caption>

## Versions are per connection

Each connection picks its own version, agreed during the TLS handshake (a field called ALPN, <Ch n="25">chapter 25</Ch>). So one request can use several versions along the way:

<Hops>
  <Hop>Shopper's browser</Hop>
  <Hop sub="HTTP/3 or HTTP/2">Google load balancer</Hop>
  <Hop sub="HTTP/1.1 or HTTP/2 inside GCP">kade-api</Hop>
</Hops>

<Caption>The slow, lossy part (the shopper's mobile network) gets the newest protocol. Inside Google's network, round trips are tiny, so the backend version matters much less.</Caption>
