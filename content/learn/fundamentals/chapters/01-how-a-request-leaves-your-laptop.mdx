## The example we follow

You open Kadé's website on your laptop at home. The page calls Kadé's API: a Node.js app running on a virtual machine (VM) called kade-api in Google Cloud (GCP). The call uses HTTPS. The full setup, with every address, is in <Ch n="0">chapter 0</Ch>.

<Figure wide hues={["plum", "teal", "green", "amber"]} drawing={<FigExample />} />

In code, it starts with one line:

```code
const response = await fetch("https://api.kade.lk/profile");
```

This asks the browser to get the `/profile` resource from the server named `api.kade.lk`, using HTTPS. Before anything can be sent, the browser and the operating system (OS) must know four values. Together they name one connection:

    <tr><td>**Source port**</td><td><Mono>52814</Mono></td><td>The OS<Sub>a free temporary port, picked per connection</Sub></td><td>Which program gets the reply<Sub>your laptop may have many open connections</Sub></td></tr>

<Caption>An IP address finds the machine. A port finds the program on that machine. Green means IP, amber means TCP, in every diagram in these notes.</Caption>

## Finding the server: DNS

Computers route by IP address, not by name. <Term>DNS</Term> (Domain Name System) is the internet's phone book: it turns `api.kade.lk` into an IP address. No single server knows every name, so the answer is found by walking a chain of servers, from the most general to the most specific.

<Figure wide hues={["plum", "teal", "green"]} drawing={<FigDns />}>

1: the browser asks the resolver "where is api.kade.lk?". 2 to 4: the resolver asks the root, then the .lk servers, then the servers that own kade.lk. 5: the answer comes back. Every step keeps a copy (cache) for a set time called the TTL, so the next lookup is much faster.

</Figure>

## Writing the HTTP request

Now the browser knows where to send. Next it writes the message itself: the <Term>HTTP request</Term>. HTTP is plain text with a fixed shape: one request line, then headers, then an empty line (and a body, for requests like POST).

<Annotated>
  <Line note="Method + path + version">GET /profile HTTP/1.1</Line>
  <Line note="Which site on the server">Host: api.kade.lk</Line>
  <Line note="Who you are (auth)">Authorization: Bearer eyJhbGciOiJIUzI1NiJ9…</Line>
  <Line note="Your session (cookies)">Cookie: session\_id=8f2a91c</Line>
  <Line note="What format you want">Accept: application/json</Line>
  <Line note="Which client is asking">User-Agent: Mozilla/5.0 …</Line>
  <Line blank note="End of headers" />
</Annotated>

<Caption>The **method** (GET) says what to do. The **path** (/profile) says what to do it to. **Headers** carry extra facts about the request. Cookies are only attached when the browser's rules allow it for that site.</Caption>

## HTTP rides on TCP

HTTP only defines what the message says. It does not move anything by itself. The moving is done by <Term>TCP</Term> (Transmission Control Protocol). TCP makes delivery reliable and in order, using mechanisms like the three-way handshake, flow control and congestion control. Each of these gets a deep-dive chapter later.

<Col title="HTTP">

What you want to say.

"Give me /profile, here is my session."

</Col>

<Col title="TCP">

<Note>

**About the "S" in HTTPS.** With HTTPS, one more layer called TLS sits between HTTP and TCP. It encrypts the HTTP text before TCP carries it, so routers on the way see only scrambled bytes. TLS gets its own chapter. For now, picture the HTTP text as sealed inside an envelope only the server can open.

</Note>

## Text becomes bytes

The network does not move text. It moves <Term>bytes</Term>. An encoder turns each character into its byte value. We usually write bytes in hexadecimal (base 16), so each byte is two characters from `00` to `FF`.

<HexLine />

Here is the whole request as the raw bytes the OS receives, in the same layout the `xxd` tool prints: position on the left, bytes in the middle, readable characters on the right.

<HexDump />

<Key title="From here on, it is only bytes">

Nothing on the path knows this was a GET request. The meaning is rebuilt only when the server decodes the bytes at the other end.

</Key>

## The browser hands off to the OS

The browser prepares the message, but it never puts anything on the network itself. It hands the bytes to the operating system's <Term>TCP/IP stack</Term>: the part of macOS, Windows or Linux that implements TCP, UDP, ICMP and IP. The OS also picks the source port. When the data is ready to go, the stack passes it to the <Term>NIC</Term> (Network Interface Card): the hardware that turns bits into signals, electrical pulses on a cable or radio waves in the air.

<Figure wide hues={["plum", "teal", "green", "amber"]} drawing={<FigHandoff />} />

<Key title="Key split">

The app prepares the message. The OS network stack transmits it. Different jobs, different layers.

</Key>

## Breaking data into chunks

Data cannot travel as one big blob. A 500-byte request or a 1 GB file is cut into many smaller chunks. Each chunk travels on its own and they are put back together at the destination. Say we have 4,000 bytes to send:

<Figure wide hues={["plum", "amber"]} drawing={<FigChunks />}>

Chunk size is limited by the MSS (below). Sequence numbers count bytes. Real connections start from a random number; we start from 1 to keep it readable.

</Figure>

Two limits decide the chunk size:

- <Term>MTU</Term> (Maximum Transmission Unit): the biggest packet a link can carry in one frame. On Ethernet and most WiFi this is 1,500 bytes.
- <Term>MSS</Term> (Maximum Segment Size): the biggest chunk of data one TCP segment can hold. It is what is left of the MTU after the IP and TCP headers.

<Figure wide hues={["plum", "teal", "green", "amber"]} drawing={<FigChunks2 />}>

Sizes in bytes, not to scale.

</Figure>

## Wrap 1: the TCP segment

Now each chunk gets wrapped, like putting a letter in an envelope. First, TCP adds its header. The result is called a <Term>TCP segment</Term>. The header holds the source port (52814), the destination port (443) and, most importantly, a <Term>sequence number</Term>.

<Envelope level="1" wide />

The sequence number is the heart of TCP's reliability. Chunks can take different paths and arrive out of order. The receiver uses the numbers to put them back in order, and to notice when one is missing:

<Table>
  <tbody>
    <tr><td><Mono>sent</Mono></td><td>**seq 1** **seq 1461** **seq 2921**</td></tr>
    <tr><td><Mono>arrived</Mono></td><td>**seq 1461** **seq 2921** **seq 1** order mixed up on the way</td></tr>
    <tr><td><Mono>rebuilt</Mono></td><td>**seq 1** **seq 1461** **seq 2921** sorted by number, a gap would mean a lost chunk</td></tr>
  </tbody>
</Table>

<Key title="First envelope">

Chunk + ports + sequence number = TCP segment. It knows which programs to connect, but not yet which machines.

</Key>

## Wrap 2: the IP packet

Next, the IP layer wraps the TCP segment and adds the source IP (192.168.1.23) and destination IP (34.87.120.15). The result is an <Term>IP packet</Term>.

<Envelope level="2" wide />

Every router on the way reads the destination IP and decides which way to forward the packet next. No router knows the full path. Each one only picks the next step, called a <Term>hop</Term>. The source IP is what lets the server know where to send the response.

<Hops>
  <Hop>Laptop</Hop>
  <Hop sub="next hop?">Home router</Hop>
  <Hop sub="next hop?">ISP router</Hop>
  <Hop sub="next hop?">… more …</Hop>
  <Hop sub="next hop?">Google edge</Hop>
  <Hop>VM</Hop>
</Hops>

<Caption>Each router asks one question of the destination IP 34.87.120.15: "which neighbour is closer to this?"</Caption>

<Note>

**A detail for a later chapter.** 192.168.1.23 is a private address. It only works inside your home network. The home router swaps it for your public IP before the packet goes to the internet. This swap is called NAT (the same idea as Cloud NAT in GCP).

</Note>

<Key title="Second envelope">

TCP segment + source and destination IP = IP packet. Now it knows which machines. This is what the internet routes on.

</Key>

## Wrap 3: the frame

The last wrap adds physical addresses, called <Term>MAC addresses</Term>. Every network card has one, for example `a4:83:e7:2b:91:0c`. The result is a <Term>frame</Term>. The frame also gets a small error check at the end (FCS) so the receiver can spot damaged frames.

<Envelope level="3" wide />

The source MAC is your laptop's NIC. But what is the destination MAC? The server is not on your local network, so you do not know its MAC, and could not use it anyway. Instead, the destination MAC is your <Term>default gateway</Term>: the home router, the device that forwards traffic out of your network.

This leads to an important pattern. IP addresses describe the whole trip. MAC addresses only describe the current step:

<Table>
  <thead>
    <tr><th>Hop</th><th>MAC addresses (frame)</th><th>IP addresses (packet)</th></tr>
  </thead>
  <tbody>
    <tr><td>Laptop → home router</td><td><Mono>a4:83:e7:2b:91:0c → 3c:84:6a:10:ee:01</Mono></td><td><Mono>192.168.1.23 → 34.87.120.15</Mono></td></tr>
    <tr><td>Home router → ISP router</td><td><Mono>router's WAN MAC → ISP router's MAC</Mono></td><td><Mono>**your public IP** → 34.87.120.15</Mono></td></tr>
    <tr><td>Every later hop</td><td><Mono>new pair every time</Mono></td><td><Mono>stays the same</Mono></td></tr>
  </tbody>
</Table>

<Caption>Bold marks what changed. The MAC pair is rewritten at every hop. The destination IP never changes. The source IP changes once, at your home router (NAT).</Caption>

<Key title="Third envelope">

IP packet + source and destination MAC = frame. The MAC gets it to the next physical device, here the router.

</Key>

## ARP, then onto the wire

The laptop knows the router's IP (192.168.1.1) from its network settings. But how does it learn the router's MAC? With <Term>ARP</Term> (Address Resolution Protocol). The laptop shouts a question to every device on the local network, and only the owner of that IP answers.

<Figure wide hues={["plum", "teal", "green", "amber"]} drawing={<FigArp />}>

The laptop saves the answer in its ARP cache, so it does not ask again for every frame. ARP is like DNS for the local network: DNS maps a name to an IP, ARP maps an IP to a MAC.

</Figure>

With the router's MAC filled in, the frame is complete. The OS hands it to the NIC, which sends it as physical signals:
