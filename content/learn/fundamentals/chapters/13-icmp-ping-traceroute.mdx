## What ICMP is

<Term>ICMP</Term> (Internet Control Message Protocol) is a helper protocol at the Internet layer. Routers and hosts use it to send status and error messages: "your packet could not be delivered", "TTL expired", "are you there?". It never carries application data.

Unlike TCP and UDP, ICMP has **no ports**. It rides directly inside an IP packet. Compare the two envelopes:

  <Seg w={1.6} hue="green">IP · protocol 6 (TCP)</Seg>
  <Seg w={1.6} hue="amber">TCP · ports 40001 → 443</Seg>
  <Seg w={2.5} hue="plum">HTTP data</Seg>
</Segments>

  <Seg w={1.1} hue="teal">frame</Seg>

  <Seg w={1.6} hue="green">ICMP · type, code, checksum</Seg>
  <Seg w={2.5} muted>small payload (no app data)</Seg>
</Segments>

<Caption>The IP header has a "protocol" field that says what is inside: 6 = TCP, 17 = UDP, 1 = ICMP. ICMP is part of the IP world (green), not a transport like TCP (amber).</Caption>

## ping

<Term>ping</Term> sends an Echo Request and waits for an Echo Reply. If the reply comes back, the host is up and reachable. The time between sending and receiving is the <Term>RTT</Term> (round-trip time): how you measure latency.

<Figure hues={["plum", "green", "amber"]} drawing={<FigPing />} />

Pinging kade-api from home:

```text
$ ping -c 4 api.kade.lk
PING api.kade.lk (34.87.120.15): 56 data bytes
64 bytes from 34.87.120.15: icmp_seq=0 ttl=57 time=41.2 ms
64 bytes from 34.87.120.15: icmp_seq=1 ttl=57 time=40.8 ms
64 bytes from 34.87.120.15: icmp_seq=2 ttl=57 time=42.0 ms
64 bytes from 34.87.120.15: icmp_seq=3 ttl=57 time=41.3 ms

--- api.kade.lk ping statistics ---
4 packets transmitted, 4 packets received, 0.0% packet loss
round-trip min/avg/max/stddev = 40.8/41.3/42.0/0.4 ms
```

  <thead>
    <tr><th>Part</th><th>Meaning</th></tr>
  </thead>
  <tbody>
    <tr><td><Mono>(34.87.120.15)</Mono></td><td>DNS ran first (<Ch n="1">chapter 1</Ch>). ping works on IPs.</td></tr>
    <tr><td><Mono>icmp\_seq=0,1,2…</Mono></td><td>Each request's number. A missing number = a lost packet.</td></tr>

<Note>

**A failed ping does not always mean "down".** kade-vpc is a custom VPC, and custom VPCs block all incoming traffic until you add firewall rules. If there is a rule for port 443 but none for ICMP, `curl https://api.kade.lk` works while ping gets no answer. Section 9 shows the rule.

</Note>

## Time Exceeded: the key to traceroute

Recall from <Ch n="12">chapter 12</Ch>: every router lowers a packet's TTL by 1. When it reaches 0, the router drops the packet and sends an ICMP **Time Exceeded** message back to the sender. That message comes **from** the router, so its source IP tells the sender exactly which router the packet died at.

## How traceroute works

<Term>traceroute</Term> uses this on purpose. It sends a probe with TTL=1: the first router lowers it to 0 and replies with Time Exceeded, revealing hop 1. Then TTL=2 reveals hop 2, TTL=3 reveals hop 3, and so on until the destination itself answers. Run it from the office front desk PC, along <Ch n="12">chapter 12</Ch>'s path. Press the button to send each probe:

## Reading traceroute output

```text
$ traceroute api.kade.lk
traceroute to api.kade.lk (34.87.120.15), 64 hops max
 1  172.16.1.1     0.9 ms   0.8 ms   1.0 ms
 2  198.51.100.1   5.8 ms   6.1 ms   5.9 ms
 3  10.200.0.2     7.1 ms   7.3 ms   7.0 ms
 4  192.0.2.2     36.4 ms  36.2 ms  36.8 ms
 5  * * *
 6  34.87.120.15  37.2 ms  37.0 ms  37.5 ms
```

<Table>
  <thead>
    <tr><th>#</th><th>You see</th><th>It means</th></tr>
  </thead>
  <tbody>
    <tr><td>1</td><td>Three times per line</td><td>traceroute sends 3 probes per TTL. Each time is the RTT to that router.</td></tr>
    <tr><td>3</td><td>A private IP (10.200.0.2) in the middle</td><td>An ISP's internal link. Normal.</td></tr>
    <tr><td>4</td><td>A jump from 7 ms to 36 ms</td><td>The link from Colombo to Singapore. A jump that **stays** for every later hop is distance or a slow link at that point.</td></tr>
    <tr><td>5</td><td>`* * *`</td><td>No answer within the time limit. Often a router that does not send Time Exceeded, or limits how many it sends. If later hops answer, the path is fine.</td></tr>
    <tr><td>-</td><td>Stars from some hop to the end</td><td>Traffic really is stopped there, or the destination's firewall blocks the probe type (section 5).</td></tr>
    <tr><td>-</td><td>One hop slow, the next ones fast</td><td>That router is just slow to _answer_ ICMP (low priority). Not a real problem.</td></tr>
  </tbody>
</Table>

<Caption>Traceroute only shows the path **to** the destination. Replies can come back another way (asymmetric routing, <Ch n="12">chapter 12</Ch>), and every RTT includes that return trip.</Caption>

`mtr` combines both tools: it runs traceroute continuously and shows loss and latency per hop, which makes a flaky hop much easier to spot than a single run.

## Destination Unreachable

Type 3 tells the sender its packet went nowhere, and the code says why:

  <thead>
    <tr><th>Code</th><th>Sent by</th><th>Kadé example</th></tr>
  </thead>
  <tbody>
    <tr><td><Mono>0 network</Mono></td><td>A router with no route for the destination</td><td>R1 loses its default route: every internet destination fails at once</td></tr>
    <tr><td><Mono>1 host</Mono></td><td>The last router: ARP for the host got no answer</td><td>The office printer is switched off</td></tr>
    <tr><td><Mono>3 port</Mono></td><td>The host itself: nothing listens on that UDP port</td><td>What traceroute's last hop sends (section 5)</td></tr>
    <tr><td><Mono>4 too big</Mono></td><td>A router: packet too big for the next link, and "don't fragment" is set</td><td>Section 8</td></tr>
  </tbody>
</Table>

## Packet too big: path MTU discovery

<Ch n="1">Chapter 1</Ch> set the MTU at 1,500 bytes. Some links carry less: VPN tunnels add their own headers, and GCP VPCs use an MTU of 1,460 by default. When a big packet reaches a smaller link, IP could split it into pieces (<Term>fragmentation</Term>), but TCP packets are normally marked "don't fragment". So the router drops it and replies ICMP type 3, code 4: "too big, the limit here is N". The sender then uses smaller packets. This is <Term>path MTU discovery</Term>.

<Table>
  <tbody>
    <tr><td><Mono>1</Mono></td><td>Office PC sends a 1,500-byte packet, "don't fragment" set, toward kade-db over the future VPN.</td></tr>
    <tr><td><Mono>2</Mono></td><td>The VPN link carries at most 1,400. The router drops it and sends **ICMP 3/4: MTU 1,400**.</td></tr>
    <tr><td><Mono>3</Mono></td><td>The PC resends in 1,400-byte packets. Everything works.</td></tr>
    <tr><td><Mono>!</Mono></td><td>If a firewall blocks **all** ICMP, step 2's message never arrives. Small requests work, but big responses hang forever. This is called a **PMTU black hole**, and it is very confusing to debug.</td></tr>
  </tbody>
</Table>

## ICMP and firewalls

Because ICMP has no ports, firewalls treat it as its own protocol, allowed or blocked as a whole or by type. Some networks block ping so their hosts are harder to discover. That is fine, but blocking **all** ICMP breaks section 8 and makes debugging much harder.

For kade-vpc, allow ping only from Kadé's own public IPs (the home and office NAT addresses from <Ch n="10">chapter 10</Ch>):

```sh
gcloud compute firewall-rules create kade-allow-icmp \
  --network=kade-vpc --direction=INGRESS --allow=icmp \
  --source-ranges=203.0.113.45/32,198.51.100.20/32
```

<Note>

**Good rule of thumb:** Echo (ping) is optional. Destination Unreachable, including "packet too big", and Time Exceeded should be allowed back in, or path MTU discovery and traceroute stop working. ICMP is also why NAT needs the ping ID (<Ch n="10">chapter 10</Ch>): with no ports, the ID is how replies find the right device.

</Note>
