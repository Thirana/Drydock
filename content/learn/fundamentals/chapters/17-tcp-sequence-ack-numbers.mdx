## Two numbers on every segment

Every TCP segment carries a <Term>sequence number</Term> (SEQ) and an <Term>acknowledgement number</Term> (ACK). Together they let both sides track exactly which bytes have been sent and which have safely arrived.

<Cols n={2}>

<Col title={"SEQ · \"this is where I am\""}>

The number of the **first byte** of data in this segment.

</Col>

<Col title={"ACK · \"this is what I want next\""}>

The number of the **next byte** the sender of this segment expects from the other side.

</Col>

</Cols>

Each direction has its own count. The laptop numbers the bytes it sends to kade-api; kade-api numbers the bytes it sends back. Every segment says both "here are my bytes from N" (SEQ) and "I have yours up to M − 1" (ACK).

## Numbers start at random

Numbers do not start at 0. During the handshake each side picks a random <Term>Initial Sequence Number</Term> (ISN), a 32-bit number. The SYN in <Ch n="18">chapter 18</Ch> really starts at 2,591,834,610.

- **Security:** an attacker who is not on the path would have to guess the current numbers to inject fake data or reset the connection. A random start makes that very hard.
- **Safety:** a new connection on the same ports will not accept stray packets from an old one, because the old numbers are far away from the new ones.

<Note>

**Wireshark shows "relative" numbers.** To keep numbers readable, Wireshark subtracts the ISN and shows the SYN as 0 and the first data byte as 1. tcpdump shows real numbers on the handshake and relative ones after. The rest of this chapter uses small numbers too (starting at 4,000 and 9,000) so the arithmetic is easy to follow.

</Note>

## SEQ counts bytes, not segments

This is the subtle, important part. If a segment carries bytes 1-50, its SEQ is 1. The next segment, carrying bytes 51-100, has SEQ = 51, not 2. The SEQ is simply the number of the first byte in that segment.

## ACK names the next byte expected

If kade-api has received bytes 1-50, it replies ACK = 51. That means: "I have everything up to byte 50. Send me byte 51 next." The ACK never lists what arrived; it names the first gap.

While waiting for the missing segment, the receiver keeps the later ones in a buffer. It cannot hand them to the app yet, because TCP promises order. This waiting is the head-of-line blocking from <Ch n="14">chapter 14</Ch>.

<Note>

**SACK (selective ACK).** A plain ACK only names the first gap. With the SACK option (agreed in the handshake, <Ch n="18">chapter 18</Ch>), the receiver can also say "I have 4201-4500 too", so the sender resends only the missing piece. Almost every modern system uses it.

</Note>

## Cumulative and delayed ACKs

ACKs are <Term>cumulative</Term>: one ACK = 4501 confirms every byte up to 4500 at once, not just one segment. This keeps overhead low. Receivers also use <Term>delayed ACK</Term>: instead of answering every segment, they usually ACK every second segment, or after a short wait (up to about 40 ms on Linux). Both appear in the "Normal" case of the simulator.

ACKs also ride on data going the other way (<Term>piggybacking</Term>). When kade-api sends its response, the same segments carry its ACK for the laptop's request, so no separate ACK is needed.

## When the numbers run out

SEQ is 32 bits, so it wraps back to 0 after 4,294,967,295 bytes (about 4 GB). That is fine: comparisons are done "around the circle". On very fast links, 4 GB can pass in a few seconds, so TCP adds a **timestamp option** to each segment to tell an old, wrapped-around segment from a new one.
