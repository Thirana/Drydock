## The question before every send

Before sending anything, a device must decide how to send it. If the target is on the same network, it sends directly: no router, no internet. If not, it hands the packet to the router (the default gateway). The <Term>subnet mask</Term> is the tool that makes this decision.

<Figure wide hues={["plum", "green", "amber"]} drawing={<FigQuestion />} />

## What a mask looks like

A mask is written like an IP address. For a /24 network it is `255.255.255.0`. The laptop got this value from DHCP (<Ch n="3">chapter 3</Ch>). But a mask is not an address: you cannot give it to a device. It exists only to be applied to addresses.

Its purpose is clear in binary. 255 is 11111111 (eight 1s) and 0 is 00000000 (eight 0s). So 255.255.255.0 is twenty-four 1s followed by eight 0s, the exact /24 split from <Ch n="3">chapter 3</Ch>:

<CidrBar ip="255.255.255.0" prefix="24" labels="1s = network bits (24),0s = host bits (8)" />

<Key title="Two ways to write the same thing">

/24 and 255.255.255.0 say the same thing. The 1s mark the network bits and the 0s mark the host bits. CIDR counts the 1s; the mask writes them out.

</Key>

## Bitwise AND

To use the mask, the device runs a <Term>bitwise AND</Term> between an IP and the mask: bit 1 of the IP with bit 1 of the mask, bit 2 with bit 2, and so on for all 32 bits. The rule for each pair:

<Table>
  <thead>
    <tr><th>IP bit AND mask bit</th><th>Result</th><th>In words</th></tr>
  </thead>
  <tbody>
    <tr><td><Mono>1 AND <Bit k="net">1</Bit></Mono></td><td><Mono>1</Mono></td><td>AND with 1 keeps the original bit</td></tr>
    <tr><td><Mono>0 AND <Bit k="net">1</Bit></Mono></td><td><Mono>0</Mono></td><td>AND with 1 keeps the original bit</td></tr>
    <tr><td><Mono>1 AND <Bit k="host">0</Bit></Mono></td><td><Mono>0</Mono></td><td>AND with 0 always gives 0</td></tr>
    <tr><td><Mono>0 AND <Bit k="host">0</Bit></Mono></td><td><Mono>0</Mono></td><td>AND with 0 always gives 0</td></tr>
  </tbody>
</Table>

<Caption>So the mask keeps the network part of an IP and wipes the host part to zeros. What is left is the network address.</Caption>

## Worked example: the laptop

<AndGrid ip="192.168.1.23" prefix="24" label="laptop" wide />

Octet by octet: 192 AND 255 = 192, 168 AND 255 = 168, 1 AND 255 = 1, and 23 AND 0 = 0. The result, `192.168.1.0`, is the network the laptop is on. This is the same address CIDR wrote as 192.168.1.0/24.

## Masks of other sizes

A /16 mask is 255.255.0.0: two octets of 1s, two of 0s. Masks do not have to end on an octet boundary. The 1s always fill from the left with no gaps, so a partly-filled octet can only be one of a few values: 128, 192, 224, 240, 248, 252 or 254.

<Table>
  <thead>
    <tr><th>CIDR</th><th>Mask</th><th>Last non-255 octet in binary</th><th>Addresses</th></tr>
  </thead>
  <tbody>
    <tr><td>/8</td><td>`255.0.0.0`</td><td>`00000000`</td><td>16,777,216</td></tr>
    <tr><td>/16</td><td>`255.255.0.0`</td><td>`00000000`</td><td>65,536</td></tr>
    <tr><td>/20</td><td>`255.255.240.0`</td><td>`11110000`</td><td>4,096</td></tr>
    <tr><td>/24</td><td>`255.255.255.0`</td><td>`00000000`</td><td>256</td></tr>
    <tr><td>/25</td><td>`255.255.255.128`</td><td>`10000000`</td><td>128</td></tr>
    <tr><td>/26</td><td>`255.255.255.192`</td><td>`11000000`</td><td>64</td></tr>
    <tr><td>/27</td><td>`255.255.255.224`</td><td>`11100000`</td><td>32</td></tr>
    <tr><td>/28</td><td>`255.255.255.240`</td><td>`11110000`</td><td>16</td></tr>
    <tr><td>/30</td><td>`255.255.255.252`</td><td>`11111100`</td><td>4</td></tr>
    <tr><td>/32</td><td>`255.255.255.255`</td><td>`11111111`</td><td>1</td></tr>
  </tbody>
</Table>

The mask also gives the last address of a range (the broadcast). Flip the mask so 1s become 0s and 0s become 1s (0.0.0.255 for a /24; this flipped form is called a <Term>wildcard mask</Term>). Then <Term>OR</Term> it with the network address (OR gives 1 if either bit is 1): 192.168.1.0 OR 0.0.0.255 = 192.168.1.255.

## In the cloud: kade-api and kade-db

The same check runs inside GCP. kade-api (10.10.1.10/24, in sn-app) wants to query kade-db (10.10.2.5, in sn-data). kade-api's network is 10.10.1.0. kade-db AND the mask is 10.10.2.0. Different, so kade-api sends to its gateway, 10.10.1.1. Change the values below to test other pairs:

<Note>

**Does a different subnet add latency?** On a physical network, going through a router adds a small delay, well under a millisecond on a local network. In GCP there is no physical router between subnets. The VPC is a software network, and the 10.10.1.1 gateway is handled by that software, not by a real box. Traffic between two subnets in the same region has practically the same latency as traffic inside one subnet. What does affect latency is distance: the same zone is fastest, then different zones in the same region, then different regions. So in the cloud, choose subnets for organisation and security (for example, separate firewall rules for the database), and keep the app and database in the same region, ideally the same zone.

</Note>
