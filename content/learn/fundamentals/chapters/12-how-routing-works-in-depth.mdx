## What routing is

<Term>Routing</Term> is moving a packet across several networks toward its destination. No single router knows the whole path. Each one makes one decision: **given this destination IP, what is the best next hop?** Then it forgets about the packet.

## The path we follow

The front desk PC in the Kadé office loads an order from kade-api. The office uses an ISP called LankaNet (made up for this course). LankaNet connects straight to Google in Singapore, and also buys general internet access from a <Term>transit provider</Term>, a bigger network that carries traffic to everywhere else.

<Figure hues={["plum", "teal", "green"]} drawing={<FigPath />}>

Each link between two routers is its own tiny network (a /30 has room for exactly 2 devices). Router interfaces are named like ge0, ge1 (gigabit Ethernet). Addresses are documentation or private ranges; the AS numbers are explained in section 10.

</Figure>

- **Destination:** a network in CIDR form (<Ch n="3">chapter 3</Ch>).
- **Next hop:** the IP of the next router, or "direct" when the destination is on a network this router is connected to.
- **Interface:** which port to send it out of.

For every packet, the router: (1) reads the destination IP, (2) finds every row it matches, (3) picks the most specific one (section 7), (4) runs ARP for the next hop (or for the target itself if "direct"), (5) builds a new frame and sends it out that interface.

## TTL: the loop safety valve

Routers make mistakes. Say LankaNet mistypes a route: R2 sends 203.0.113.99 to R3, and R3 sends it back to R2. Without a limit, a packet for that address would bounce forever, and millions of them would fill the links.

<Figure hues={["plum", "amber"]} drawing={<FigTtl />} />

So the IP header carries a <Term>TTL</Term> (Time To Live), a number that each router lowers by one. At 0 the router drops the packet and tells the sender with an ICMP message. Common starting values: 64 (Linux, macOS), 128 (Windows), 255 (many routers). <Ch n="13">Chapter 13</Ch> turns this safety valve into a tool: traceroute.

A destination can match several rows. R3, LankaNet's border router, has these routes (among others):

    <tr><td><Mono>34.87.0.0/16</Mono></td><td><Mono>192.0.2.2</Mono></td><td><Mono>ge1</Mono></td><td>Google directly: "34.87.x is mine"</td></tr>

34.87.120.15 matches all three. The router always picks the **most specific** match: the one with the longest prefix, meaning the most network bits that agree. Bit by bit:

<LpmBits ip="34.87.120.15" routes="0.0.0.0/0,34.0.0.0/8,34.87.0.0/16,198.51.100.0/24" />

The /16 wins, so the packet goes straight to Google over the direct link, not the long way through the transit provider. This is good for LankaNet too: direct links with Google are usually cheaper and faster than paid transit.

<Key title="The rule">

Of all matching routes, the longest prefix wins. A /32 beats a /24, which beats a /16, which beats a /8, which beats the /0 default. <Ch n="5">Chapter 5</Ch>'s laptop table works the same way: /24 for the LAN beats /0 for everything else.

</Key>

## When two routes have the same length

Longest prefix match comes first. Only if two matching routes have the same prefix length does the router need a tie-breaker:

<Table>
  <tbody>
    <tr><td>**1 · Trust in the source**</td><td>Routes learned in different ways get a trust score (Cisco calls it **administrative distance**; lower wins). Typical values: connected 0, static 1, BGP from another network 20, OSPF 110, RIP 120.</td></tr>
    <tr><td>**2 · Metric**</td><td>Among routes from the same protocol, the one with the lower cost wins (fewer hops for RIP, faster links for OSPF).</td></tr>
    <tr><td>**3 · Still equal: ECMP**</td><td>Equal-Cost Multi-Path: the router uses all of them and spreads traffic. It keeps each connection on one path, so packets are not reordered.</td></tr>
  </tbody>
</Table>

<Caption>GCP uses a simpler version: each VPC route has a **priority** number, and among routes of the same length the lowest number wins. Equal priorities are spread with ECMP.</Caption>

## The default route

What if nothing matches? Routers use a <Term>default route</Term>, 0.0.0.0/0: "when in doubt, send it here". It matches every address with 0 bits, so it always loses to anything more specific. It is the last resort, not the first choice.

## Static and dynamic routing

Routing tables are filled in two ways:

<Cols n={2}>

<Col title="Static routes">

Typed in by hand. Simple and predictable. Fine for small setups like R1's one default route.

Problem: if a link fails, nothing updates itself.

</Col>

<Col title="Dynamic routes">

Routers tell each other which networks they can reach, using a <Term>routing protocol</Term>, and update their tables when links fail or return.

</Col>

</Cols>

<Table>
  <thead>
    <tr><th>#</th><th>Protocol</th><th>Used</th><th>How it chooses</th><th>In our path</th></tr>
  </thead>
  <tbody>
    <tr><td>1</td><td>RIP</td><td>Small, older networks</td><td>Fewest hops (max 15)</td><td>Not used</td></tr>
    <tr><td>2</td><td>OSPF</td><td>Inside one organisation</td><td>Every router learns the full map of links and computes the fastest path</td><td>R2 and R3 inside LankaNet</td></tr>
    <tr><td>3</td><td>BGP</td><td>Between organisations: the whole internet</td><td>Policies and paths between networks, not just speed</td><td>R3 with Google and the transit provider</td></tr>
  </tbody>
</Table>

The internet is a network of networks. Each organisation that runs its own routing is an <Term>autonomous system</Term> (AS) with a number: Google is AS 15169. <Term>BGP</Term> is how they tell each other "these address ranges are reachable through me":

<Figure hues={["teal", "green", "amber"]} drawing={<FigDynamic />}>

Green: announcements that build R3's table from section 7. Amber: LankaNet's own announcement, which is how Google knows where to send kade-api's replies to 198.51.100.20. Traffic flows the opposite way to announcements. AS 64500 and 64510 are numbers reserved for examples.

</Figure>

## Other routing ideas you will hear

<Table>
  <tbody>
    <tr><td>**Asymmetric routing**</td><td>The reply may take a different path from the request. Each router decides on its own, and kade-api's reply is routed by Google's and LankaNet's tables, not by the original path. Keep this in mind when reading traceroute (<Ch n="13">chapter 13</Ch>).</td></tr>
    <tr><td>**Route summarization**</td><td>Announcing one bigger range instead of many small ones. The office could announce 172.16.0.0/16 instead of 172.16.1.0/24 and 172.16.2.0/24. Smaller tables, fewer updates.</td></tr>
    <tr><td>**Blackhole (null) route**</td><td>A route whose next hop is "drop it". Used to throw away attack traffic, or to stop a summary route from looping.</td></tr>
    <tr><td>**Routing table vs forwarding table**</td><td>Protocols build the routing table (all known routes). The router copies only the winners into a fast forwarding table used for each packet.</td></tr>
  </tbody>
</Table>

## Where latency comes from

Three words get mixed up all the time:

<Table>
  <thead>
    <tr><th>Word</th><th>Meaning</th><th>Home → kade-api</th></tr>
  </thead>
  <tbody>
    <tr><td>**Latency**</td><td>How long one piece of data takes to get there. Usually quoted as round-trip time (RTT).</td><td><Mono>41 ms RTT</Mono></td></tr>
    <tr><td>**Bandwidth**</td><td>The most a link can carry per second. A property of the link.</td><td><Mono>100 Mbit/s (your plan)</Mono></td></tr>
    <tr><td>**Throughput**</td><td>What you actually get per second, after windows, loss and sharing (<Ch n="19">chapters 19</Ch>-<Ch n="20">20</Ch>).</td><td><Mono>anything up to 100 Mbit/s</Mono></td></tr>
  </tbody>
</Table>

<Caption>A faster plan raises bandwidth. It does not lower latency to Singapore at all.</Caption>

Every packet's delay is the sum of four parts, at every hop:

<Table>
  <thead>
    <tr><th>#</th><th>Delay</th><th>Caused by</th><th>Size on our path</th><th>Can you reduce it?</th></tr>
  </thead>
  <tbody>
    <tr><td>1</td><td>**Propagation**</td><td>Distance. Light in fibre covers about 200 km per millisecond.</td><td>~35 ms of the 41 (Colombo ⇄ Singapore)</td><td>Only by moving closer: a nearer region, a CDN, anycast (section 15)</td></tr>
    <tr><td>2</td><td>**Transmission**</td><td>Pushing the bits onto the link: packet size ÷ link speed</td><td>1,500 bytes at 100 Mbit/s = 0.12 ms</td><td>Faster links; matters on slow links</td></tr>
    <tr><td>3</td><td>**Queuing**</td><td>Waiting behind other packets in router queues</td><td>0 to hundreds of ms (bufferbloat, <Ch n="20">chapter 20</Ch>)</td><td>Better queues, less congestion</td></tr>
    <tr><td>4</td><td>**Processing**</td><td>Routers reading headers; the server doing its work</td><td>microseconds per router; kade-api's own time on top</td><td>Faster code (for the server part)</td></tr>
  </tbody>
</Table>

## Anycast: one IP, many places

Normally one IP address belongs to one machine in one place: <Term>unicast</Term>. With <Term>anycast</Term>, the **same** address range is announced over BGP (section 10) from many locations at once. Every router simply follows its best route, so each user reaches the **nearest** location without knowing others exist.

<Table>
  <thead>
    <tr><th>#</th><th>Kind</th><th>One sender reaches</th><th>Example</th></tr>
  </thead>
  <tbody>
    <tr><td>1</td><td>Unicast</td><td>one specific host</td><td>kade-api today at 34.87.120.15</td></tr>
    <tr><td>2</td><td>Broadcast</td><td>every host on the local network</td><td>ARP requests, DHCP Discover</td></tr>
    <tr><td>3</td><td>Multicast</td><td>every host that joined a group</td><td>Live video inside a company network</td></tr>
    <tr><td>4</td><td>Anycast</td><td>the **nearest** of many hosts sharing one IP</td><td>1.1.1.1, 8.8.8.8, Cloudflare, Google's global load balancers</td></tr>
  </tbody>
</Table>

<Figure hues={["plum", "green", "amber"]} drawing={<FigAnycast />}>

Later in the course, api.kade.lk moves to a GCP global external load balancer, which gets one anycast IP (34.120.7.9 here is an example). TCP and TLS then end at the nearest Google edge, so the handshakes (<Ch n="16">chapter 16</Ch>) happen over a short distance, and the long part of the trip runs over Google's own network.

</Figure>

- **Failover for free:** if one location stops announcing the route, BGP sends users to the next-nearest one.
- **Spreads attacks:** a DDoS aimed at one IP lands on many locations at once.
- **Works for TCP** because internet routes rarely change in the middle of a connection. It was first used for DNS (short UDP exchanges), and still is.
