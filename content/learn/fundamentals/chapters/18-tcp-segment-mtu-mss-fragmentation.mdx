## The header layout

A TCP header is **20 bytes** before options, and up to 60 with them. It carries everything TCP needs: ports, the two numbers from <Ch n="17">chapter 17</Ch>, control flags, the receive window and a checksum. Compare UDP's two rows (<Ch n="15">chapter 15</Ch>):

## The window: flow control

Every segment carries the sender's <Term>receive window</Term>: "I have room for N more bytes". The other side must never have more than N unacknowledged bytes in flight. If kade-db is busy and its buffer fills, it advertises a smaller window, down to 0 ("stop"), then a bigger one again when it catches up. This is flow control from <Ch n="16">chapter 16</Ch>.

The window also limits speed. At most one window of data can be sent per round trip, so:

<Equation>max speed ≈ window ÷ round-trip time</Equation>

<Table>
  <tbody>
    <tr><td>64 KB window, home → kade-api (41 ms)</td><td><Mono>65,535 × 8 bits ÷ 0.041 s ≈ **12.8 Mbit/s**, even on a 100 Mbit/s line</Mono></td></tr>
    <tr><td>With window scaling (e.g. 3 MB)</td><td><Mono>≈ **600 Mbit/s**: now the line is the limit</Mono></td></tr>
  </tbody>
</Table>

<Caption>The window field is only 16 bits (max 65,535). The **window scale** option (section 6) multiplies it, which is how fast long-distance transfers work today.</Caption>

<Part n="B">How big can a segment be?</Part>

## MTU

The <Term>MTU</Term> (Maximum Transmission Unit) is the largest packet a link can carry in one piece. For classic Ethernet and most WiFi it is 1,500 bytes (<Ch n="1">chapter 1</Ch>). Anything bigger must be split before it can cross that link. Different links have different MTUs:

<Table>
  <tbody>
    <tr><td>Home WiFi, office Ethernet</td><td><Mono>1,500</Mono></td></tr>
    <tr><td>kade-vpc (GCP's default)</td><td><Mono>1,460 <Sub>can be set to 1,500 or up to 8,896</Sub></Mono></td></tr>
    <tr><td>A VPN tunnel (office → cloud, later)</td><td><Mono>less, e.g. 1,400: the tunnel adds its own headers</Mono></td></tr>
    <tr><td>Some home fibre / DSL links (PPPoE)</td><td><Mono>1,492</Mono></td></tr>
  </tbody>
</Table>

<Caption>The **path MTU** is the smallest MTU of any link on the whole path. That is the real limit.</Caption>

## MSS

The <Term>MSS</Term> (Maximum Segment Size) is the largest amount of **application data** one TCP segment can carry. It is the MTU minus the IP and TCP headers:

<Equation>1,500 MTU − 20 IP − 20 TCP = 1,460 MSS</Equation>

- **Each side announces its MSS in the SYN** (section 6), based on its own link. Each then sends segments no bigger than what the other side announced.
- **Options eat into it.** With the timestamp option on every segment (12 bytes with padding), each full segment really carries 1,448 bytes of data.
- **Inside GCP**, MTU 1,460 gives MSS 1,420, so kade-api and kade-db use smaller segments than your laptop.

TCP uses the MSS to slice your byte stream. When kade-api sends a 4,000-byte order list to your laptop:

## Fragmentation

If an IP packet is still too big for a link's MTU, the IP layer can <Term>fragment</Term> it: split it into smaller IP packets, which are put back together only at the final destination. The IP header has fields just for this:

<Table>
  <tbody>
    <tr><td>Identification</td><td>The same number on every fragment of one packet, so they can be matched</td></tr>
    <tr><td>DF flag (Don't Fragment)</td><td>"Do not split me" (section 10)</td></tr>
    <tr><td>MF flag (More Fragments)</td><td>1 on every fragment except the last</td></tr>
    <tr><td>Fragment offset</td><td>Where this piece's data starts, counted in 8-byte units</td></tr>
  </tbody>
</Table>

<Caption>Fragment data must be a multiple of 8 bytes (except the last), so fragment 1 carries 1,376, not 1,380. Each fragment gets its own 20-byte IP header, so the total grows from 1,500 to 1,520.</Caption>

Fragmentation works, but it is avoided:

- **Lose one fragment, lose the whole packet.** TCP must resend the entire segment.
- **Extra work** for routers and for the receiver, which must hold fragments until all arrive.
- **Firewalls and NAT struggle:** only the first fragment contains the TCP/UDP ports.
- **IPv6 routers never fragment at all.** Only the sender may.

## DF and path MTU discovery

To avoid fragmentation, hosts use <Term>PMTUD</Term> (Path MTU Discovery), which <Ch n="13">chapter 13</Ch> introduced from the ICMP side. TCP sends every packet with the **DF** bit set. A router that cannot forward it without splitting must drop it and send back ICMP type 3, code 4 ("fragmentation needed", with the next link's MTU). The sender lowers its segment size for that destination:

<Note>

**The classic mystery stall.** If a firewall blocks those ICMP messages, PMTUD breaks. The handshake works (small packets), the HTTP request works (small), then the first big response never arrives and the connection just hangs. Two fixes: allow ICMP type 3 through firewalls (<Ch n="13">chapter 13</Ch>), and on VPN routers use **MSS clamping**: the router rewrites the MSS option in passing SYNs to a size that fits the tunnel, so large segments are never sent at all. Newer systems can also probe for the right size without relying on ICMP.

</Note>

## Why tcpdump shows giant segments: NIC offloads

Capture on your own laptop or on kade-api and you may see TCP segments of 30,000 or 64,000 bytes, far above the 1,460 MSS, and "bad checksum" warnings on packets you sent. Nothing is broken. Modern network cards take over some of TCP's work, and tcpdump watches from a point **before** the card does it:

<Table>
  <thead>
    <tr><th>#</th><th>Offload</th><th>Direction</th><th>What happens</th><th>What tcpdump shows</th></tr>
  </thead>
  <tbody>
    <tr><td>1</td><td>**TSO / GSO** (segmentation offload)</td><td>sending</td><td>The OS hands the card one big chunk (up to 64 KB). The card cuts it into MSS-sized segments and copies the headers onto each.</td><td>One huge "segment", e.g. `length 65160`</td></tr>
    <tr><td>2</td><td>**GRO / LRO** (receive offload)</td><td>receiving</td><td>The card or driver merges many arriving segments of one connection into one big one before the OS sees them.</td><td>Big segments arriving too</td></tr>
    <tr><td>3</td><td>**Checksum offload**</td><td>sending</td><td>The card fills in the TCP/UDP checksum just before sending (<Ch n="15">chapter 15</Ch>).</td><td>`incorrect` or `bad` checksum on outgoing packets only</td></tr>
  </tbody>
</Table>

To see the real on-the-wire segments, capture on another machine, a switch mirror port, or (for a quick test only) turn the offloads off with `ethtool`. Cloud VMs use the same tricks on their virtual network cards.
