<Part n="A">Where TLS fits</Part>

## HTTPS = HTTP inside TLS

<Term>TLS</Term> (Transport Layer Security) wraps a connection so that traffic is private and tamper-evident. <Term>HTTPS</Term> is not a different protocol: it is plain HTTP (<Ch n="24">chapter 24</Ch>) running inside a TLS-encrypted connection. Everything about HTTP still applies; TLS just protects it in transit. (SSL is TLS's old name; all SSL versions are broken and switched off.)

## How HTTP, TLS and TCP fit together

TLS sits between HTTP and TCP. HTTP hands its bytes to TLS; TLS encrypts them into **records** and hands those to TCP; TCP delivers them reliably (<Ch n="16">chapters 16</Ch>-<Ch n="20">20</Ch>):

  <Seg w={1.3} hue="green">IP header</Seg>
  <Seg w={1.3} hue="amber">TCP header</Seg>
  <Seg w={1.3}>TLS record header</Seg>
  <Seg w={3} hue="plum">encrypted HTTP request</Seg>
  <Seg w={.9}>auth tag</Seg>
</Segments>

<Caption>Encryption alone is not enough. Without authentication you could have a perfectly encrypted conversation with an attacker. Part C is about how the third guarantee works.</Caption>

<Part n="B">The cryptography</Part>

## Symmetric encryption: fast, one shared key

In <Term>symmetric encryption</Term>, the same key locks and unlocks. Modern ciphers like **AES** (sped up by special CPU instructions) and **ChaCha20** (fast on phones without them) encrypt gigabytes per second per CPU core. TLS 1.3 uses them in **AEAD** mode ("authenticated encryption"): each record is encrypted and gets a tag that proves it was not changed, in one step.

The catch: **both sides need the same key**, and they have never met. Sending the key over the network would let anyone listening read everything after it.

## Asymmetric cryptography: key pairs

In <Term>asymmetric</Term> (public-key) cryptography, each party has a **key pair**: a **private key** kept secret and a **public key** shared with everyone. What one key does, only the other can undo. It is used in two ways:

<Cols n={2}>

<Col title="Signatures">

Sign with the **private** key; anyone checks with the **public** key. Proves "the owner of this key made this, and it was not changed".

TLS use: kade-api proves it owns its certificate.

</Col>

<Col title="Key exchange">

Two sides each combine their own private value with the other's public value and arrive at the **same secret**, without ever sending it.

TLS use: laptop and kade-api agree on the symmetric key.

</Col>

</Cols>

Asymmetric operations rely on hard maths (large-number and elliptic-curve problems), which makes them **thousands of times slower** than symmetric encryption. Fine for a few operations per connection; far too slow for every byte of a video.

## Key exchange: agreeing on a secret in public

The idea behind TLS's key exchange is <Term>Diffie-Hellman</Term>. Both sides agree on public numbers, each picks a private number, and they swap only the results. Anyone listening sees the swapped values but cannot work out the shared secret, because undoing the maths is extremely hard at real sizes. Try it with tiny numbers:

<DhCalc />

Real TLS uses the elliptic-curve version (ECDHE, usually the curve X25519) with 256-bit numbers. The "E" means **ephemeral**: fresh private numbers for every connection, thrown away afterwards (section 9).

## Why TLS uses both

    <tr><td>4</td><td>Every record after</td><td>Symmetric AEAD (AES-GCM or ChaCha20-Poly1305)</td><td>Encrypt and protect all HTTP data</td><td>Fast enough for every byte</td></tr>

<Caption>Slow, clever maths a few times per connection to set things up; fast, simple maths for everything else. This split is called **hybrid encryption**.</Caption>

## The TLS 1.3 handshake

After the TCP handshake, the laptop and kade-api run the TLS handshake:

<SeqDiagram set="tls13" />

<Table>
  <tbody>
    <tr><td>**ClientHello**</td><td>Supported TLS versions and **cipher suites**; a **key share** (the laptop's public ECDHE value); the server name **SNI** = api.kade.lk (section 12); **ALPN** = "h2, http/1.1" (<Ch n="24">chapter 24</Ch>); a random number.</td></tr>
    <tr><td>**ServerHello**</td><td>The chosen suite (e.g. `TLS_AES_128_GCM_SHA256`) and kade-api's key share. Both sides can now compute the shared secret: **everything after this is encrypted**.</td></tr>
    <tr><td>**Certificate**</td><td>kade-api's certificate chain (Part C).</td></tr>
    <tr><td>**CertificateVerify**</td><td>A signature over the whole handshake so far, made with the certificate's private key. This is the proof: a stolen copy of the certificate is useless without the private key.</td></tr>
    <tr><td>**Finished**</td><td>Each side sends a check value over the whole handshake, so any tampering with the hellos (like forcing a weaker cipher) is detected.</td></tr>
  </tbody>
</Table>

<Caption>TLS 1.3 needs **1 round trip**. TLS 1.2 needed 2 and sent the certificate unencrypted. TLS 1.0 and 1.1 are switched off everywhere; allow 1.2 and 1.3 only.</Caption>

## Forward secrecy

Because the key-exchange numbers are ephemeral, each connection's keys exist only in memory for that connection. If an attacker records today's traffic and steals kade-api's private key next year, they **still cannot decrypt** the recording: the private key was only used to _sign_, never to protect the session keys. This is <Term>forward secrecy</Term>. TLS 1.3 always has it. Old TLS 1.2 setups with "RSA key exchange" did not: there, one stolen key opened every recorded session.

## What a certificate is

A <Term>certificate</Term> is a signed statement: "this public key belongs to api.kade.lk", signed by someone the browser already trusts. The format is called **X.509**. kade-api's certificate (as issued for the load balancer later):

<Caption>The certificate is public: the server sends it to everyone. The **private key** is the secret, and protecting it is what matters.</Caption>

## The chain of trust, and SNI

Browsers and operating systems ship with a **trust store** of about 150 root CA certificates. Roots are kept offline and rarely used; they sign **intermediate** CAs, which sign server certificates. The server sends its own certificate plus the intermediates; the client builds the chain up to a root it already trusts:

<Figure hues={["plum", "green"]} drawing={<FigChain />} />

One IP often serves many sites (a load balancer or Cloudflare). Before any certificate is sent, the server needs to know which one to pick, so the ClientHello includes the name: <Term>SNI</Term> (Server Name Indication). SNI is sent in clear text, which is how the café can see the site name even over HTTPS. A newer extension, Encrypted ClientHello (ECH), hides it where both sides support it.

## Lifetimes, renewal and revocation

- **Short lifetimes.** ACME certificates last 90 days, and the industry has agreed to cut the maximum for all public certificates in steps, down to 47 days by 2029. Short lives limit the damage from a leaked key. Renewal must be automated: an expired certificate is one of the most common causes of outages.
- **Revocation.** If a private key leaks, the certificate should be revoked before it expires. Clients learn about revocations through lists (CRLs) or an online check (OCSP), which the server can attach to its handshake ("OCSP stapling"). In practice browsers check unevenly, which is another reason for short lifetimes.

## Certificate Transparency

Every publicly trusted certificate must be written to public, append-only **Certificate Transparency** (CT) logs, and browsers refuse certificates that are not logged. So Kadé can search the logs (for example on crt.sh) for every certificate ever issued for kade.lk, and spot one it did not request. Attackers use the same logs to discover new subdomains, so do not rely on a secret-sounding name like `admin-7f3.kade.lk` to hide anything.
